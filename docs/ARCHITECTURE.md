# FireTrident architecture

FireTrident is a git platform for many coding agents working one repository at once, built on Cloudflare Workers and Artifacts. It coordinates agents the way colonies do: through signals left in a shared environment, local decisions, and parallel integration, instead of locks and one merge queue.

## The model in one screen

- **Colony**: one codebase. A trunk repository in Artifacts plus the coordination state around it.
- **Field**: decaying marks on regions of the code (claim, need, trail, failure, danger). Agents read the field instead of messaging each other. Reading it costs the same no matter how many agents there are.
- **Intent**: what should change and why, declared before any code is written, with a predicted footprint (the paths it expects to touch).
- **Rule (morphology)**: a declared architecture rule. Every violation becomes a need in the field and an intent.
- **Workspace**: an Artifacts fork leased to one agent with a short-lived, workspace-scoped token. Agents never hold a trunk write token.
- **Proposal**: an intent's change: base and head commits in the workspace, the files written (write set), the files read (read set), declared footprint, and evidence.
- **Lane**: a region's integration queue. Each cycle it picks the largest set of non-conflicting, still-valid proposals and hands them to the trunk writer, which lands them as one commit.
- **Inline changes** (`core/changeset.ts`, `colony/inline.ts`): a proposal may carry `contents`, the text of every file it writes keyed by git blob id; its head is `changesetId(baseSha, writeSet)`, and `inlineProblem` checks it (every text hashes to its blob, text only, at most 64 files and 512 KB). The colony keeps the texts in `proposal_contents` until the proposal settles; the decide stage, contest judging and the trunk writer read them there, never a workspace. The API (`contents` on `POST /proposals`) and MCP (`propose` with `files`) accept them when `FT_INLINE` covers the colony. Every take still leases a workspace repository, inline changes included, so a run of thousands of agents leaves about one workspace repository per agent until its colony is deleted.
- **Lineage**: every landed commit carries `FT-*` trailers and a JSON note under `refs/notes/firetrident` with the intent chain, read and write sets, decisions, and evidence. Secret-looking text in a note's free-text fields (what the agent did not verify, check details, directives, decision questions and answers) is replaced with `[masked]` before the note is written (`trunk/mask.ts`). Each proposal's entry carries `provenance` (`trunk/provenance.ts`), computed by the trunk writer from the colony's record of the agent, never from the proposal: `author` (`platform`, `external`, `synthetic`), `auth` (`platform`; for an external agent `mcp` when it holds a resume key, `token` otherwise) and `model` with its evidence: `observed` for in-platform agents, named after the model their calls went to (an intent may ask for one that is not the agent's own) and with the calls and tokens the agent loop counted; `declared` for every other. The API refuses to register an in-platform agent (they start through `POST /swarm`) or to propose for one. A note names its landing, never its commit, so it is final before the commit is built, and the commit carries its digest as its last trailer: `FT-Note: sha256:<hex>`, over the masked note as written to git, without `certification` (`trunk/digest.ts`). `TrunkDO.verifyNotes` (`trunk/verify.ts`; `GET /api/colonies/:id/notes/verify`, public; `ft verify <colony>`) compares the newest notes on `refs/notes/firetrident` with their commits' trailers and reports each `intact`, `altered` or `missing`; `scripts/verify_note.mjs` does the same with stock git. `TrunkDO.verifyLanding` (`GET /api/colonies/:id/notes/verify?landing=<landing id or commit>`) checks one landing's note, and every note in the Why tab shows the result as a badge (intact, altered, or landed before notes were sealed). `GET /api/colonies/:id/landings/:ref/diff?path=` returns a landing's change to one file, at most 64 KB, for colonies listed in `FT_PUBLIC_GIT` or `FT_PUBLIC_MCP` and 404 for any other; the Why tab shows it behind "Show the change". With `FT_NOTE_KEY` (a Worker secret holding an Ed25519 private key as a JWK), the trunk writer signs each commit it builds (`trunk/signature.ts`): `FT-Note-Signature: ed25519 <key id> <signature>`, just above FT-Note, over `firetrident-note-signature v1`, the note's digest, the tree and the parents. `/.well-known/firetrident-keys.json` publishes the public key (its id is the first 16 hex digits of the SHA-256 of the key) and `/api/about` names it; the note checks, `ft verify`, the Why badge and `scripts/verify_note.mjs --keys <url>` say signed, bad signature or unsigned. Without the secret, commits are built exactly as before. The landing page's signed card and the colony top bar read the same check and `/.well-known/firetrident-keys.json`.

## Request flow (an in-platform agent)

1. `ColonyDO.registerAgent` gives the agent an id.
2. `ColonyDO.take(agentId)` builds candidates from open intents, reads the field from the relevant `RegionDO`s, and picks one with the response-threshold rule (`core/threshold.ts`). Three signals shape the choice:
   - **Lateral inhibition**: a candidate whose exact footprint files carry live claims from other agents above a threshold (half a fresh claim by default) is skipped. Claims decay, so a silent agent's claim stops inhibiting after about two half-lives: there is no lock to release and nothing to deadlock.
   - **Co-change repulsion** (soft): TrunkDO mines trunk history into a Hebbian co-change map (`core/cochange.ts`, `trunk/cochange.ts`); candidates whose files usually change together with files other agents have claimed score lower.
   - **Admission**: `RegionDO.admit` checks the region's admission cap and deposits the agent's `claim` marks in one synchronous step, so concurrent takes cannot over-admit a region. Only then does `PoolDO.lease` hand out a workspace.

   The assignment also says what review will ask of the change (`review`, `agents/preview.ts`): the questions of up to five live antibodies whose path matchers cover the footprint, and the rules that cover it. An agent sees a pattern people rejected before it writes it. Security antibodies are left out: an agent whose change one of them returns is told only the class, never the question that would show how to slip past it.

   It also says why the code is the way it is (`context`): the latest landings, at most three, that changed the footprint's files, with their intents' titles and whys, from a per-path index the colony fills as landings arrive (no trunk call per take).

   And it says why the intent's latest change came back (`lastReturn`): the proposal, when, the paths it wrote and the reason its agent was given, unless a change for the intent has landed since. Direction returns and contest losses are skipped, and a security return names only the class. In-platform agents see it as fenced data to address first; MCP `take` and `checkout` return it as `lastReturn`. A change that came back because trunk moved its files names the landings that moved them (`movedBy`: the landing, its intent's title and why, its agent, the model its note names and the trunk commit), on the proposal, in the inbox, in take's `lastReturn`, in the redo prompt (fenced as data) and on the web cards, and its reason ends: keep what that landing did unless your intent says otherwise, and escalate if both cannot hold.

   - **Import repulsion** (`FT_IMPORT_WEIGHT`, off when absent or 0): claims on the direct imports and importers of a candidate's files repel it the way co-change neighbors do. TrunkDO keeps the import index (`trunk/imports.ts`, `importLinks`) current from landings; a take asks for it once per batch of files, cached, and fails open. In the simulator it cut rework from 31% to 16% at weight 1, for about 10% fewer landings a minute (bench results 2026-10-13-papers). Where nothing conflicts it is pure cost: on a preview, the Hono rule run (20 Gemma agents, 0 returns either way) took 199 s to zero at weight 1 against 137 s and 143 s without it, so it stays off unless a colony's work contends on hub files.
3. The agent (`AgentDO`) clones trunk at `lease.baseSha` into a `@cloudflare/computer` Workspace using the read-only trunk token, reads its footprint's files and the files its intent builds on (each recorded in its read set with its blob id; the project tree its write prompt lists, up to 400 paths, and the modules its import check reads are not recorded), edits with an LLM, commits, and force-pushes its commit to `main` of its own workspace repo with the workspace write token. The fork's prior content never matters. (At very large scale agents read from trunk mirrors instead of trunk, to respect per-repo git request limits.) With virtual checkouts (`FT_VIRTUAL_CHECKOUT`: `on` or colony ids) an agent never clones: it reads the commit, the root tree, the subtrees along each wanted path and then the blobs through the `ARTIFACTS` binding at `lease.baseSha`, cached by id (`agents/virtual.ts`), and proposes an inline change: no commit and no push. A change over the inline limits, or with binary content, still goes the git way for that change.
4. `ColonyDO.propose` records the proposal, computes the residual (paths changed outside the declared footprint), runs innate checks, and enqueues it in the lane of the proposal's primary region (`RegionDO.enqueue`).
5. On each lane tick (`RegionDO` alarm, interval from `core/batch.ts#laneIntervalMs`), the region asks `TrunkDO.blobsFor` for current trunk blobs, validates proposals with `core/occ.ts`, selects a batch with `core/batch.ts#selectBatch`, and calls `TrunkDO.land(batch)`. Stale proposals are returned to their agents with each stale path, the blob it read and the blob now on trunk.
6. `TrunkDO.land` queues the batch. One cycle at a time takes every waiting batch (up to 200 proposals), re-validates each proposal against trunk and the batches ahead of it, reads each proposal's new blobs from its workspace repo (`readBlob` on the binding), or, for inline changes, their texts from the colony in one call per cycle (checking each blob id), builds one commit per batch on top of the previous one by replacing only the changed paths (`FT-*` trailers, a lineage note each), and pushes the tip once with the expected old value (compare-and-swap) (with asynchronous publishing, `FT_ASYNC_PUBLISH`, the cycle records its landings and moves the trunk writer's own main instead, and a publish loop beside the cycles pushes every commit recorded since its last push, in order: leases, `certified` and the lineage notes follow the published head, lanes validate against the recorded one, the recorded head stays within 2,000 landings or 60 s of the published one, a restart publishes first, and a take whose intent covers a file changed by an unpublished landing waits half a second instead of leasing a base without it); the notes follow in one notes commit on `refs/notes/firetrident`. The lane then reports each `Landing` to `ColonyDO.onLanding`, which updates intents, deposits `trail` marks, reinforces the agent's threshold for the region, and broadcasts events.

## Durable Objects and their RPC contracts

All are SQLite-backed (`new_sqlite_classes`). Callers use RPC on stubs (`env.COLONY.get(env.COLONY.idFromName(colonyId)).take(agentId)`). Types come from `@fire_trident/core`.

### ColonyDO (name: colonyId)
Owns colony config, intents, rules, agents, proposals index, review queue, antibodies, decision counters (the funnel), metrics, and the live WebSocket hub (hibernation API) for the UI. It also prices the colony's model calls (`colony/spend.ts`, `core/pricing.ts`): in-platform agents count calls and tokens per model in their journals, which the colony reads into its own tables (16 at a time, at most every 15 s, until an agent has stopped and been quiet 5 minutes), and review, the contest judge, the conflict resolver and antibody minting count theirs per model as they call. `GET /api/colonies/:id/metrics` and `GET /api/colonies/:id` carry `spend`: USD in total, by layer (agents, review, judge, resolver, other) and per landed intent, tokens by model, and the tokens of any model with no listed price, which count in no dollar sum; prices are Workers AI list prices on 2026-10-12. The top bar, `ft status` and the landing page's rule card show it. Tokens counted before the per-model counters existed are priced at the model their layer is set to use (review at Clef, second opinions at the dearest second-opinion model).
- `init(p: { colonyId; name; trunk: RepoRef; trunkSha: Sha; source?; regionDepth? }): Promise<Colony>`
- `snapshot(): Promise<ColonySnapshot>`
- `addIntent(i: Omit<Intent, "id" | "status" | "createdAt">): Promise<Intent>` (also deposits `need` marks)
- `addRule(r: Omit<Rule, "id" | "createdAt">): Promise<{ rule: Rule; violations: number; intents: number }>`
- `registerAgent(a: { kind: AgentKind; name: string; model?: string }): Promise<AgentInfo>`
- `take(agentId: Id): Promise<{ intent: Intent; lease: WorkspaceLease; rule?: Rule; review?: ReviewPreview } | { wait: true; retryInMs: number; reason: string }>`
- `getProposal(id: Id): Promise<Proposal | null>` (agents poll their outcome)
- `getRule(id: Id): Promise<Rule | null>`
- `heartbeat(agentId: Id): Promise<void>` (refreshes claim marks)
- `propose(p: Omit<Proposal, "id" | "status" | "createdAt" | "evidence"> & { evidence?: Partial<Evidence> }): Promise<Proposal>`
- `updateProposal(id: Id, patch: Partial<Proposal>): Promise<void>` (called by RegionDO/TrunkDO)
- `onLanding(l: Landing): Promise<void>`
- `review(): Promise<Array<Proposal & { review?: ReviewView }>>` (each escalated proposal with its masked review view), `decide(proposalId: Id, d: "approve" | "reject" | "return", reason: string, by: string): Promise<void>`
- `emit(e: ColonyEvent): Promise<void>` (broadcast to UI sockets; also used by other DOs)
- `fetch(req)`: WebSocket upgrade for `/api/colonies/:id/live`

### RegionDO (name: `${colonyId}:${region}`)
Owns the field for one region and that region's lane.
- `configure(p: { colonyId: Id; region: string }): Promise<void>`
- `deposit(marks: Array<Omit<Mark, "id">>): Promise<void>`
- `clear(filter: { agentId?: Id; intentId?: Id; kind?: MarkKind; paths?: Path[] }): Promise<number>`
- `reading(): Promise<FieldReading>`
- `enqueue(p: Proposal): Promise<void>`
- `recordCause(e: { id: string; causeId?: string; at: number }): Promise<void>` (criticality governor)
- `alarm()`: lane tick

### TrunkDO (name: colonyId)
The only writer of trunk. Holds a `@cloudflare/computer` Workspace with trunk cloned, an index of trunk paths to blob ids, and the lineage tables.
- `init(p: { colonyId: Id; trunk: RepoRef }): Promise<{ trunkSha: Sha; files: number }>`
- `files(): Promise<Array<{ path: Path; size: number; blob: Sha }>>`
- `blobsFor(paths: Path[]): Promise<Record<Path, Sha | null>>`
- `readFile(path: Path): Promise<string | null>`
- `baseBlobs(baseSha: Sha, paths: Path[]): Promise<FileVersion[]>`
- `land(batch: Proposal[]): Promise<{ landing?: Landing; returned: Array<{ proposalId: Id; reason: string }> }>`
- `why(path: Path, line?: number): Promise<Array<{ landing: Landing; note: LineageNote }>>`
- `landings(limit?: number): Promise<Landing[]>`
- `revert(ref: string, p: { by: string; reason: string }): Promise<RevertResult>` (see "Changing direction")
- `markCertified(sha: Sha): Promise<boolean>` (see "Trunk certification")

### PoolDO (name: colonyId)
Keeps a warm pool of workspace forks of trunk across the `ft-ws-*` namespaces. Each namespace holds a seed repo that mirrors trunk `main`, and workspaces fork from their namespace's seed (forks cannot cross namespaces, and forking a repo just pushed fails about one time in five: spike/RESULTS.md facts 2 and 3). Workspaces are refreshed to the current trunk on lease and recycled after landing.
- `init(p: { colonyId: Id; trunk: RepoRef; target: number }): Promise<void>`
- `lease(agentId: Id, trunkSha: Sha): Promise<WorkspaceLease | null>`
- `release(agentId: Id): Promise<void>`
- `status(): Promise<{ ready: number; leased: number; forking: number; target: number }>`

### AgentDO (name: agentId)
An in-platform agent built on `@cloudflare/computer` (a git workspace) and Workers AI (or Claude when `ANTHROPIC_API_KEY` is set). It loops: take, work, propose, wait, repeat. Its model gets no tools: the loop reads the files and records the read set (request flow step 3). It journals each step so a killed agent resumes.
- `start(p: { colonyId: Id; agentId: Id; model: string }): Promise<void>`
- `stop(): Promise<void>`, `status(): Promise<AgentInfo>`

### FireTridentMcp
An `agents/mcp` McpAgent exposing tools for external agents (any MCP client): `join`, `sense`, `take`, `declare`, `checkout`, `read`, `propose`, `inbox`, `release`, `escalate`, `why`, `impact`. Every tool call heartbeats the agent's claims, so a slow external agent keeps its work; an agent silent for ten minutes loses its intent to the colony. `take` and `inbox` accept `wait` (the server waits for work or for the proposal's outcome). `join` registers the session as an external agent and returns a `resumeKey` once (the colony keeps only its SHA-256); another session acts as that agent only with `agentId` and that key. `take` returns git steps that need no shell state (no `cd` or `export`), and with `checkout` the questions review will ask of the change, the rules that cover it and the why of the latest landings on its files; `escalate` reports an intent that cannot be done as written (see Escalations); `propose` records the agent's `notVerified` statement for review; `why` trims each note to the proposals that wrote the path (`otherProposals` counts the rest). Session state tolerates parallel tool calls. A failed call returns `isError` with `structuredContent.error` and the same JSON as its text (`mcp/errors.ts`): `kind` (`validation`, `auth`, `not_found`, `conflict`, `too_large`, `rate_limit`, `server`, `unavailable`), `message`, `retryable`, `retryAfterMs` (a jittered 1 to 5 s for platform failures such as an overloaded object), `status`, and `next` where the next call is clear. `declare` remembers each call's fingerprint (title, why, sorted footprint, acceptance, priority, parent) in the session's object for ten minutes, and a repeat returns the same intent with `replayed: true`; `take`, `declare`, `propose`, `release` and `escalate` are annotated idempotent. `impact` lists a file's importers up to three levels (at most 200 files, each with the import it comes `via`), the live claims on them (agent, intent and claim age, read from at most 32 regions) and the whys of up to 10 recent landings on them; it labels agent-written text as data and fails open (the import index gets 3 s to sync, or the answer says it may be behind). It also answers on the public MCP for listed colonies, as `GET /api/colonies/:id/impact?path=` and as `ft impact`. With `FT_MODEL_STEPUP` (`on` or a list of colony ids), an intent whose changes came back twice since it last changed course is taken next with the stronger model class (`default`): the take says why, an in-platform agent uses it and its note's observed model shows the switch, and an outside agent gets it as advice; a third return still reaches the stuck strip. Beside MCP, with `FT_A2A` (`on` or a list of colony ids) an orchestrator hands a colony work over the Agent2Agent protocol (`api/a2a.ts`, `colony/a2a.ts`): a public agent card at `GET /api/colonies/:id/.well-known/agent-card.json` and JSON-RPC at `POST /api/colonies/:id/a2a`, where `SendMessage` declares an intent (the first line of the text is the title, the rest the why; data parts may carry the footprint and acceptance) and needs the admin token, `GetTask` and `ListTasks` follow intents as tasks without one (open is submitted, claimed or proposed is working, landed is completed with the commit and a link to the why, withdrawn by `CancelTask` is canceled, withdrawn otherwise or escalated and not approved is failed), and `CancelTask` withdraws (admin token). A twin answer returns the existing intent's task and says so. See `docs/agents/a2a.md`.

## Artifacts layout

- `ft-trunk` namespace (binding `ARTIFACTS`): `<colony>--trunk` and, later, lane repos `<colony>--lane-<region>`.
- `ft-ws-0..3` namespaces (bindings `WS0..WS3`): workspaces `<colony>--ws-<n>`, sharded by `n % 4` to spread the per-namespace control-plane limit.
- `ft-sessions` namespace (binding `SESSIONS`): one repo per in-platform agent session.

Measured in the spike (spike/RESULTS.md): import and fork are synchronous (about 1.3 s per fork, parallel even from one source); about 20% of forks issued within ~0.1 s of a push to the source fail with INTERNAL_ERROR and must be retried; git inside a Durable Object via `@cloudflare/computer` clones in ~350 ms, commits in ~90 ms, and pushes in ~300 ms; a commit built by tree surgery takes ~40 ms; forks copy every ref including notes (`defaultBranchOnly` is ignored); binding read calls need `main` or a full commit id (`HEAD` and `refs/...` return null); the server rejects pushes whose expected old value is stale (compare-and-swap) but accepts forced non-fast-forward pushes; the namespace push trigger starts a Workflow for every repo in the namespace (~0.5 s to instance, ~2.3 s to `run()`).

Facts the design relies on (from the docs and the spike): each repo is one Durable Object; git requests are limited per repo and control-plane calls per namespace; the binding reads but cannot write files, so writes go through git; there is no server-side merge, hook, or branch protection; Artifacts accepts non-fast-forward pushes, so only TrunkDO ever holds a trunk write token and it pushes with an expected old value.

## Live events

`ColonyEvent` (see `packages/core/src/types.ts`) is the single event shape for the UI and for internal fan-out. The UI first loads `ColonySnapshot`, then applies events from the WebSocket.

## Additional RPCs (as built)

- ColonyDO: `getColony`, `listRegions`, `getIntent`, `getAgent`, `registerAgents` (batch), `abandon(agentId, reason)`, `inbox(agentId, limit, opts?)` (proposals and directives), `updateProposals` (batch), `recordDecision`, `landContext(intentIds, agentIds, proposalIds?)` (compact lineage context for lanes: intents with their direction, agents, recorded decisions). Changing direction: `amendIntent`, `withdrawIntent`, `retractRule`, `direct`, `recall`, `relay`, `intentHistory` (see "Changing direction").
- AgentDO: `direct({ directive, intent? })` (a directive pushed by the colony; see "Changing direction").
- RegionDO: `reading(opts)` (optionally filtered by paths), `apply`, `dequeue`, `status`.
- TrunkDO: `init` accepts an optional `regionDepth`; `land(batch, ctx?)` takes compact lineage context (lanes pass it, so the writer never pulls a snapshot); `stats`, `flushNotes` (re-pushes any note whose push failed after its landing), `mirrorTo`, `refreshTokenIfNeeded`. TrunkDO does not call `onLanding`; the lane does.
- PoolDO: `stats`, `teardown`. Forks cannot cross namespaces, so each `ft-ws-N` namespace holds a seed repo `<colony>--seed` that workspaces fork from.
- AgentDO: `start({ colonyId, agentId, model?, kind?, name?, delayMs? })`; `status()` returns AgentInfo plus journal fields.
- RegionDO: `configure({ colonyId, region, regionDepth })`; `admit` (atomic admission plus claim deposit, see request flow step 2); `landedFor(paths)` answers which landing last changed a path, so a stale return with no local cause records the landing in another region as its parent (the cascade detector sees cross-region causes).
- TrunkDO: `neighbors(paths)` and `cochangeStats()` read the co-change map; `landingsOf`, `systemCommit` (antibodies and reverts; a file may name the blob it expects to replace, and a mismatch refuses the whole commit). `verifyLanding(ref)` and `landingNote(ref)` (one landing's note check, and the writer's copy of its note for the diff route), `protect(globs)` (the protected globs every cycle reads) and the impact walk over the import index.
- **Assumptions.** The decide stage records on each proposal the trunk files its new or rewritten relative imports resolve to (`assumptions`, its own writes excluded). `planCycle` returns a proposal whose assumption is gone from the virtual trunk (deleted on trunk, or by a batch ahead in the cycle) and one that would delete a assumption of a proposal accepted earlier in the cycle, so a deletion and a new import of the same file never both land in one cycle (a deletion that lands in a later cycle is caught by the deletion guard when it is on, otherwise only by certification). Only existence counts.
- **Import-name revalidation** (`FT_REVALIDATE`: `on`, or a comma-separated list of colony ids; off when absent). The decide stage also records `nameAssumptions`: for each trunk file a change's relative imports resolve to, the names it imports from it. A change that is stale only because files it read changed (none it writes, no file or directory clash) lands when every such file is covered by a name assumption and every name is still exported on the virtual trunk (the lane passes it on, and `planCycle` decides from export lists read from blobs, cached by blob id). Its lineage note records `revalidated` (path, blob read, blob landed on, the names that held), and a `revalidated` event is published. Namespace, side-effect and dynamic imports, `export *`, non-script and sensitive files are not covered, so a change relying on them goes back as before. Names are not enough on their own: each file the change read must also have only grown since the version it read (`decide/statements.ts`): every top-level statement of the read version is still present, token for token and in order, in the version the change lands on, and whatever is new is a declaration (the prologue of imports and directives stays in place). A changed or missing statement sends the change back naming the file and the first such line; a file whose statements cannot be cut reliably (top-level control flow, labels, decorators without a class, JSX, an ambiguous slash, more than 20,000 statements) sends it back too. The note's `revalidated` entry gains `grew: true`. What a new declaration does at load time is not checked: certification is the backstop. The cycle reads the blob each stale read saw as well, within the same `SURFACE_READS` and `SURFACE_BYTES`. Checked on a preview (2026-10-13) with the cascade scenario on Hono, 30 readers importing `Hono` from `src/hono.ts` while a writer added an export to it: with revalidation on, 0 of 30 went back and all landed on their first proposal; with it off, 30 of 30 went back, σ peaked at 29 and the region was inhibited 14 times.
- **Text merge** (`FT_TEXT_MERGE`: `on`, or a comma-separated list of colony ids; off when absent). A proposal stale only on files it writes (`textMergeCandidate`: each with a blob on its base, on trunk and in the proposal) passes the lane and the trunk writer's screen, and `planCycle` merges each such file line by line against the virtual trunk, trunk or a version landed earlier in the same cycle (`core/textmerge.ts`: git's default rules; line endings, final newline and BOM kept; at most 1,000 changed lines a side). When every file merges cleanly the proposal lands with the merged blobs, which later proposals in the cycle see; the landing and the lineage note record `merged` (path, base, trunk, theirs, result), and the trunk writer counts `trunk.merged`. A conflict sends it back as before, naming the conflicting hunks and their lines. Binary files, lockfiles and files over 512 KB are never merged, and the trunk writer loads at most 400 blobs and 8 MB of text a cycle for merges. Checked on a preview (2026-10-14, `packages/bench/results/2026-10-14-round5/`): two agents editing lines 2 and 11 of one file from the same trunk both landed, the second as a merge whose result is the text with both edits; with text merge off it went back stale; two edits to line 6 ended with one landing and the other back, naming the hunk. With `FT_MERGE_INSERTIONS` (`on` or a list of colony ids), conflicting hunks that are insertions by both sides at one place land as their union, trunk's lines first, recorded as `rule: "insertions"` in `merged` and counted in `trunk.mergedInsertions`; a line of the change is left out as already inserted only when it is a whole statement or entry standing alone in both insertions (`core/insertions.ts`), so shared braces and blank lines stay.
- **Conflict resolver** (`FT_RESOLVER`: `on` or a list of colony ids; `FT_RESOLVER_MODEL`, default `FT_DEFAULT_MODEL`). Where the flag covers the colony, a change sent back because text merge found overlapping hunks carries the conflicts (path, base, trunk and theirs blobs, hunk lines) through its lane to the colony (`colony/resolver.ts`), which holds the intent for the platform agent `resolver` and tells the change's agent. One model call through the decide limiter sees each conflicting file with conflict markers, fenced as data, and returns its whole merged text keeping both changes, or `CANNOT: <reason>`. The merge must keep every line outside the conflicting hunks as the clean merge has it, take neither side's version of a hunk whole, still parse, and touch no other file (`colony/resolver-merge.ts`); then it is proposed inline for the same intent, through review like any change, with provenance `platform` and the model `observed`, and its note records `resolves` (the returned change, the landings it merged with, the files). Any failure, a 60 s timeout or a second return lets the original return stand and reopens the intent. At most 20 resolutions an hour and 2 at once per colony; metrics `resolver.attempted`, `resolver.landed`, `resolver.failed`. Checked on a preview (2026-10-14, `scripts/resolver.ts`): two edits of one line from one trunk, the second sent back, then merged with both edits kept and landed; with the resolver off it went back as before. The merge must also keep every line either change added inside a conflicting hunk, in that change's order (a line may be rewritten only where it rewrites a base line the other side also changed); a merge that drops or reorders one is refused, naming the line and its place in the base.
- **Megafile alarm** (`FT_MEGAFILE`: `on` or a list of colony ids). From landings and returns (`colony/megafile.ts`, `core/hotness.ts`), a script file (tests excluded) turns hot at 600+ lines with 25% growth and 4+ distinct writers within 30 minutes, or after 6+ returns that wrote it. A hot file gets one split intent (source `system`, priority 8, footprint the path, `dir/*` and `dir/stem/**`, acceptance: every name it exports stays importable from it) and a hold: take skips other intents whose footprint covers it, a change that writes it goes back at propose (with review off too), and changes already on their way go back when the hold begins. The hold lifts when the split lands, is withdrawn or escalated, after 60 minutes, or when a person releases it (`POST /api/colonies/:id/megafile {path, action}`, `ft megafile`); the colony's status lists held files, and the split's evidence carries the file's lines before and after into its note. Checked on a preview: a file grown from 650 to 830 lines by five agents was held, its in-flight changes went back, the split landed (830 → 3 lines, all 69 exports kept) and the hold lifted.
- **Field guide** (`FT_FIELD_GUIDE`: `on` or a list of colony ids). An agent may leave a `lesson` (at most 300 characters) with a proposal: MCP or REST `propose`, or an in-platform `LESSON:` line after the file. It is cleaned, masked like note text and kept as a candidate with the proposal's provenance (`colony/guide.ts`, `core/guide.ts`). It becomes active at the first green certification of a commit at or after its landing, or when a person approves it (`POST /api/colonies/:id/guide/:lessonId`, `ft guide`), and is dropped when its landing is reverted, a red certification names its change, its change comes back, or a person rejects it. At most 30 active lessons and 6,000 characters (the oldest retires); near-duplicates are refused. `take` and `checkout` carry the newest active lessons (up to 4,000 characters) as `guide`, and prompts fence them as data under a label that says who wrote each and the landing it came from. Checked on a preview (`scripts/field_guide.ts`): a lesson went active on its landing's green certification and reached the next agent's take with its provenance; a reverted landing's lesson was dropped.
- **Deletion guard** (`FT_DELETION_GUARD`: `on`, or a comma-separated list of colony ids; off when absent). In a cycle that deletes trunk files, the trunk writer brings its import index (`trunk/imports.ts`) up to date and sends back a change that deletes a file while a trunk file's import of it would resolve to nothing after the cycle, naming up to ten importers ("deleting src/b.ts breaks the imports of src/a.ts: change them in the same change, or first"). Importers that the same change, or one accepted ahead of it in the cycle, deletes or rewrites so they no longer import the file do not count. Imports resolve as revert's guard resolves them (relative specifiers; path aliases and packages are not followed). Only cycles that delete files pay: locally, on Hono's 569 files, the first such cycle took about 150 ms more (building the index) and later ones about 1 ms. It fails open: when the index cannot be brought up to date within 3 s, the cycle runs without it. Removing an export is guarded by the export guard when it is on (next).
- **Export guard** (`FT_EXPORT_GUARD`: `on`, or a comma-separated list of colony ids; off when absent; `trunk/exportguard.ts`). In a cycle that changes trunk script files, the trunk writer reads the names each changed file exports before and after (cached by blob id); for a name it stops exporting, it asks the import index which trunk files import that file and reads their imports (the same 3 s budget, at most 400 blobs and 8 MB). A change goes back while a file still imports the removed name and neither the change nor one accepted ahead of it in the cycle rewrites that file: "removing export foo from src/b.ts breaks the import in src/a.ts: change src/a.ts in the same change, or first". A removal and a new import of the same name never land in one cycle: the second goes back naming the first. Whatever it cannot read for sure (an index that is not current, `export *` in either version, CommonJS, path aliases the index does not see) it skips and counts as `trunk.exportsUncovered`; it never sends back on a guess.
- **Derived indexes** (`trunk/derived.ts`): every index derived from the landing log shares one mechanism: a name, a version, eager or lazy, an idempotent `apply` per landing and a cursor in `ft_derived`. Eager indexes apply each landing in the landing hook; lazy ones catch up from their cursor when read, in bounded slices; a version bump rebuilds from the log; a landing that cannot be applied is skipped and logged. TrunkDO: the import index (eager), the co-change map and path history (lazy; `pathHistory(path)` answers who changed a path without reading notes). ColonyDO: the why-context index (eager).
- `destroy()` on RegionDO, TrunkDO, PoolDO and AgentDO wipes the object's storage and alarms; `DELETE /api/colonies/:id` calls them.
- `deprovisionTrunk()` in `artifacts/colony.ts` removes a colony's repos.
- MCP: `/mcp` (Streamable HTTP) and `/sse`, gated by `FT_MCP_TOKEN`, sent as an `Authorization: Bearer` header and compared in constant time; a `token` query parameter is refused, and without the secret the endpoint refuses connections. `/public/mcp` (`mcp/public.ts`) is a stateless, read-only MCP for the colonies `FT_PUBLIC_MCP` lists (`status`, `why`, `intent`, `sense`, `impact`, each taking `colony`; no token, no `join`), and answers 404 when the variable lists none. Its tools reach only read methods and serve what the public read routes serve (remotes hidden, security return reasons withheld); a request is capped at 64 KB and 8 messages, a call at 15 s, and an isolate at 32 requests in flight. With `FT_AGENT_CALL_BUDGET` (`on`: 4 tool calls a second, 20 at once after a pause; or `<rate>,<burst>`), each MCP session has a token bucket (`mcp/budget.ts`): a call that finds it empty answers `rate_limit` (429, retryable after the time until a token is back) without running, so it never reaches the colony. The bucket lives in the session object's memory, so a new session starts full. Checked on a preview with the bench scenario `flood` (16 greedy sessions polling `inbox` without `wait` against 4 honest agents): 63,444 of 71,418 greedy calls were refused before the colony (7,974 reached it, against 56,450 with the budget off), and the honest agents landed at the same rate with no refusals.

## Decide: the reflex arc and the immune review (packages/worker/src/decide/)

A proposal enters `checking` and the decide engine routes it:

1. **Innate checks**: the rule re-check on the changed files (every live rule, the intent's own first, up to 200), residual paths (changed but not in the declared footprint), a mandatory "Not verified:" statement, and hollow files: a new script file that is empty or holds only comments or placeholder bodies goes back.
2. **Deterministic proof**: every changed relative import is resolved against the trunk file tree. When only import specifiers changed and each still points at the same file, the rule re-check passes, the change stays inside its footprint and touches no sensitive path, the proof is a confirmation on its own and no model is consulted. A broken import is returned with the exact path. The resolution facts are passed to every model that is consulted, and no model opinion can override them. A change whose every changed file is an existing script file with the same tokens outside comments and whitespace is proven not to change behavior (`decide/comments.ts`, an exact lexer; JSX, any directive comment and credential-looking new comments disqualify it), and lands on the innate checks plus this proof (the colony policy's `commentProof`, on by default).
3. **System 1 (reflex)**: one Clef call (`@cf/cloudflare/clef`, typed noul/choice/score questions: needs_human, risk, touches_sensitive, off_intent, plus every matching antibody question). Confident answers act; uncertain ones escalate.
4. **System 2 (LLM)**: consulted only when the deterministic proof is inconclusive and the reflex cannot act alone. A second opinion from a different model family than the authoring agent (`@cf/google/gemma-4-26b-a4b-it`, or `@cf/openai/gpt-oss-120b` when the author is Gemma), strict JSON verdict, behind a per-model concurrency and rate limiter with backoff and fallback (Workers AI caps large models at 20 requests a minute per account). Reviewers see up to 24,000 diff characters a file and 60,000 in all. An approval counts as a confirmation only when the layer saw every changed line; a change too large for its view goes to a person ("too large for model review"), and each layer's view (files shown of files changed, what was cut) is recorded with its decision. The state models see says who wrote the intent's why: a person, a rule, certification or an agent, whose why is a claim to check. Every model prompt (second opinion, contest judge, antibody questions) puts the intent, the agent's own text, the facts and the diff inside one fence marker that occurs in none of them, labeled as data to judge, never instructions.
5. **System 3 (human)**: the review queue.

`propose` is idempotent: a repeat for the same agent, intent and head commit returns the existing proposal. Deterministic outcomes are recorded as their own checks in the evidence and in `decide.deterministic.*` metrics; they never count as reflex decisions in the funnel.

**Loosened guards** (`danger.ts`): in modified script files (not tests), deleted 401/403 denials and throws inside security conditions, security conditions made weaker (an operand dropped, `===` turned into `==`, a negation removed, a constant comparison dropped), `verify` swapped for `decode` or a constant-time compare dropped, and deleted expiry or limit checks are a `loosened-guard` signal: a second opinion must look, and no intent text, policy or antibody waives it. Measured on real history (`packages/bench/results/2026-10-13-danger`, every modified non-test script file checked on its own): on Hono, the loosened-guard signal fired on 13 of 3,559 files (0.4%), 12 of them in auth, JWT, CSRF or signed-cookie code, and on none of Hono's newest 251 commits; all the danger checks together flagged 1.1%. On FireTrident's own history they flagged 9.5%, mostly Durable Object SQL calls (`sql.exec(...)`) that the process pattern reads as running a program, which sends them to a person. How often the checks miss a dangerous change nobody has seen is not measured.

**Protected paths** (rule P3): the colony policy's `protectedPaths` (globs; `GET`/`POST /api/colonies/:id/decide/policy`, `ft policy --protect`) send any change that writes, deletes or renames a matching path to a person, naming the glob, in every phase and even with review off; no intent text, antibody or policy waives it. A glob added later reaches changes already cleared to land: each lands only with a person's approval given after protection, checked by the colony, each lane and every trunk-writer cycle (`TrunkDO.protect`, table `ft_protected`), and the policy answer says which changes were stopped and which had already landed.

**Twin intents** (`FT_TWINS`: `on` or a list of colony ids; `core/twins.ts`, `colony/twins.ts`). An intent a person or an agent declares (REST or MCP `declare`) is compared with the colony's open, claimed and proposed intents and those landed in the last 30 minutes: when its normalized title words score at least 0.8 (Jaccard, after punctuation, stop words and do-it verbs are dropped and words lightly stemmed) against one and their footprints overlap, nothing is created; the answer names the twin (`duplicateOf`, `similar`) with a sentence saying to take it or declare again with `force: true`. Removing never matches adding, rule, certification, spec and vaccine intents are never checked, and `ft new` declares with `force`.

**Goal conflicts** (rule P4, `FT_GOAL_CONFLICT`: `on` or a list of colony ids). A change that removes lines a recent landing wrote for another intent waits for a person: in a text file it modifies or deletes, it removes at least max(3, half) of the lines that landing still has there, the landing is within the decide policy's `goalConflictMinutes` (60) and among its newest `goalConflictLandings` (200), and its intent is neither an ancestor nor a descendant of the change's own (`core/goalconflict.ts`). Blank lines and re-indented lines do not count. The trunk writer traces the removed lines through its landing log and notes (`TrunkDO.removedLineOwners`, bounded to 20 files, 2,000 lines, 512 KB and 4 s). The reason names the landing, its age, its intent and why; a person approving lands the change with `undoes` in its note. Certification repairs, rule intents, the colony's own intents (megafile splits) and the platform's own commits never conflict, and the check fails open: its own failure never holds a change, and the evidence says it was not checked. Agents are also told to escalate with `contradictory-spec` instead of undoing another intent's recent work. Checked on a preview (`scripts/goal_conflict.ts`): three agents each moving one backend to a different language; with the check, the first landed and the other two waited, each naming the landing it would undo, and a person chose; without it, all three landed and the last silently won. `scripts/goal_conflict.ts --demo <colony>` sets up the same three goals on one colony with an agent assigned to each and never decides anything: the first change lands and the two that would undo it stay with a person. Production's `order-backend` colony is that demo.

**Two-signal gate** (`gate.ts`): a proposal lands without a person only on two confirmations bound to its head commit: the innate checks, plus a deterministic proof that it changes nothing but what its rule asks, a second model's approval of every changed line, or earned autonomy with a confident, quiet reflex. On the proof path both confirmations are deterministic and rest on a rule a person wrote: the proof passes only when the innate checks pass, and p(needs_human) is not consulted (Clef's alarms are advisory there; an antibody hit still returns the change). A second model's approval and earned autonomy also need a low p(needs_human). Earned autonomy applies only to intents written by a person or a rule, and only when the reflex saw the whole change. One signal returns it to its agent. Escalation to a human needs a detector hit plus damage or a capability change. **Regulation**: an alert budget caps human pages per hour; a detector marked not useful ≥10% goes advisory and >25% goes off. **Danger patterns** (`danger.ts`): hits for new process, network, eval or crypto use are waived only when an intent written by a person or a rule asks for them; an agent's or a repair's text never waives them. In a repair intent from certification, any test-file change beyond imports is a must-human hit no policy or antibody can waive, and node:test's skip and todo forms, and assertions that disappear (commented-out ones do not count), are test-weakening. **Security returns**: a return for a security finding tells its agent only the class; the full reasons stay in the decision record and the review view, the proposal route withholds them from readers without the operator token, and the intent's next proposal goes to a person. **Antibodies**: a human rejection mints an antibody (path matcher + yes/no question + threshold) only when no existing antibody fired on the proposal (otherwise it counts a recurrence on the one that did), committed to trunk as `.firetrident/antibodies/<id>.json` by `TrunkDO.systemCommit` with a lineage note; every later matching proposal is screened, and the return reason names the antibody's question. Antibody files are authoritative: a landing that edits, renames or deletes one reloads or retires it. **Vaccination meter**: `POST /api/colonies/:id/vaccinate {count}` injects sealed bad proposals of several threat classes through the normal path; they can never land, and recall per class is reported with a Wilson 95% interval (`GET /api/colonies/:id/vaccinate`). The report separates vaccines returned (stopped by a model or a check) from vaccines escalated (sent to a person, whose decision the meter does not measure), and a vaccine whose second opinion was unavailable is an error, not a catch. **Review view**: for every escalated proposal the engine keeps a masked view in `decide_review` (each file's hunks up to 24,000 characters, 60,000 in all, the danger hits with line numbers, the residual paths; lines that may hold a secret are masked), the review queue serves it, and the web card and `ft review` lead with the lines to look at first.

**Quoted acceptance** (`FT_QUOTED_ACCEPTANCE`: `on` or a list of colony ids; `decide/quotes.ts`, `decide/acceptance.ts`). For an intent with an acceptance list, the second opinion answers each line as met, not met or unclear, naming a file and quoting at least 8 characters of a changed line for each met; the acceptance list is fenced as data in the prompt. The platform looks for each quote, whitespace-collapsed, in the diff it showed the model (a quote it cannot find, or one from a removed line, counts as unclear), and the approval counts as a confirmation only when every line is met with a found quote. A line not met returns the change naming it (so does a keep line: the acceptance of the newest landing by another intent on the files the change modifies); an unclear one goes to a person. The decision, the lineage note, `ft why`, the Why tab and the public MCP `why` keep each line with its verdict and quote. Rule intents on the proof path, certification repairs and vaccines keep today's rule.

Routes: `POST|GET /api/colonies/:id/vaccinate`, `GET /api/colonies/:id/immune`, `POST /api/colonies/:id/decide/policy`, `POST /api/colonies/:id/detectors/:did` (useful / not useful feedback). ColonyDO: `vaccinate`, `vaccineReport`, `immune`, `setDecidePolicy`, `detectorFeedback`. Every decision is recorded (`recordDecision`) and emitted, so the UI funnel shows reflex / LLM / human counts. `GET /api/colonies/:id/immune` is public: each autonomy row gives the approved landings since the region's last revocation, that revocation's reason and when the region last moved (`lastAt`); the Review tab shows them latest first ("Autonomy earned in N of M regions"), and `ft immune <colony>` prints them with the antibodies and detectors.

## Changing direction (chemotaxis)

A colony is steered the way cells follow a chemical gradient: when the gradient changes, cells re-orient. Here a human changes the gradient (amends an intent, withdraws it, retracts a rule, or sends an agent guidance), the field updates (needs evaporate, move or appear), and agents re-orient at their next step. Nothing is preempted by a lock or a queue. Agents also tell the colony what they are doing, so a human can see where to push. Pure helpers live in `colony/direction.ts` (colony side) and `agents/direction.ts` (agent side).

**Amend** (`PATCH /api/colonies/:id/intents/:iid {title?, why?, footprint?, priority?, reason, by?}`, `ColonyDO.amendIntent`, `ft intent amend`). The intent's `revision` goes up by one and the change is kept in `intent_revisions` (fields changed, before and after, reason, by, at). Need marks move with the footprint (strength = priority) and claims leave the paths it dropped; the holder's claim follows the paths it gained. A title, why or footprint change is **substantive**: changes in flight built on the older revision go back (`intent revised: r1 → r2, why changed (...)`), and the holder keeps the intent, claim and lease and redoes the work against the new revision. A priority-only amendment just moves the intent in the queue. Landed, withdrawn and sealed intents cannot be amended (409); `GET /api/colonies/:id/intents/:iid` (`ft intent show`) returns the intent with its revisions and directives.

**Withdraw** (`POST .../intents/:iid/withdraw {reason, by?}`, `ft intent withdraw`). The intent becomes `withdrawn` (kept, with the reason), its need marks evaporate and its claims clear, changes in flight go back (`withdrawn: ...`), and its holder goes idle and gives its lease back. Idempotent. **Retract a rule** (`DELETE /api/colonies/:id/rules/:rid {reason, by?}` or `?reason=`, `ft rule retract`): the rule stays in history (`retractedAt`, `retractedBy`, `retractReason`) but is no longer checked (the decide arc and agents skip it), its open violations stop counting, and every intent it created that has not landed is withdrawn. Landed work is never touched.

**Directives** (`POST /api/colonies/:id/agents/:aid/directive {message, intentId?, by?}`, `ColonyDO.direct`, `ft direct`). Free-text guidance for one agent, about the intent it holds unless `intentId` names another. Revisions and withdrawals reach the holder the same way, as directives of kind `revision` and `withdrawal`. An in-platform agent gets them pushed (`AgentDO.direct`); external agents read them in their inbox (`ColonyDO.inbox`, which the MCP `inbox` tool calls): a directive entry lines up with a proposal entry (`id`, `intentId`, `status: "directive"`, `reason` = what to do, `createdAt`). Reading a revision notice records that the agent saw that revision.

**How an in-platform agent re-orients** (`loop.ts`, `applyDirection`). Directives are kept in the agent's journal and acted on before its next step. A withdrawal ends the job (the colony already released the claim). A revision ends it too, and the next take hands back the same intent at the new revision. Guidance joins every later prompt for that intent (a "Directives from a human operator" block); work already produced is redone with it, after the agent recalls a proposal still in flight (`ColonyDO.recall`: returned as `superseded: ...`, intent, claim and lease kept). A directive that makes the step in flight moot (any withdrawal or revision of the job's intent, guidance while it produces or proposes) moves the agent's epoch, so the step halts at its next check and no more model calls go the old way.

**When a change of direction takes effect.** An amendment or withdrawal sends changes in flight back and dequeues them; `ColonyDO.propose` refuses (409) a change built on an older substantive revision (an external agent passing no `intentRevision` is held to the revision it last saw); the lane returns stale direction before `TrunkDO.land`. The commit point is the trunk writer: the colony records the new direction with `TrunkDO.direction` (table `ft_direction`), and each landing cycle reads it once before building. Recorded before that read, the change stops; after it, the change lands, and the call waits for that cycle (at most 15 s) and names the landing, which `ft revert` undoes. Responses give `returned` (changes stopped), `landed` (each with its landing and trunk commit) and `confirmed` (false when the trunk writer did not answer, so those changes may still land). A withdrawal that lost the race leaves the intent landed; an amendment that lost it keeps the intent live ("landed a change built on r1; r2 still to do"). Direction returns leave no failure mark, are not counted by the cascade detector, count as `redirected` (not `returned`), and never reopen the intent. `scripts/direction_race.rb` checks both outcomes on a deployment, with `FT_TEST_PUSH_DELAY_MS` holding each push open. Checked on a preview (2026-10-13) with the push held 6 to 10 s: 7 withdrawals that arrived after the cycle's check were each answered with their landing, and trunk agreed; 2 sent while the change waited in the writer's queue stopped it. The first queued try found that the colony recorded the withdrawal at the trunk writer only after telling the lanes, whose dequeue can wait behind a landing in flight, so the change's own cycle never saw it; the colony now starts `TrunkDO.direction` first.

**Relay** (`POST /api/colonies/:id/agents/:aid/status {note}`, `ColonyDO.relay`). An agent's one-line "what I am doing now" is stored on the agent (`GET agents` and `ft agents` show it in the NOW column), emitted live (at most one event per agent per second), and recorded with its next proposal. In-platform agents relay as they enter each step and when they act on a directive (at most every 3 s; synthetic agents at most once a minute).

**Lineage.** At propose time the colony records the direction a change was built under in its evidence (`evidence.direction`: `intentRevision`, the amendments up to it, the human guidance the agent had for the intent, its last status note), so it lands in the lineage note under `refs/notes/firetrident`. `landContext(intentIds, agentIds, proposalIds)` also hands the lane each proposal's recorded decide-arc decisions (layer, kind, p, action, at, the question, who answered, a one-line answer; the latest 8 per proposal), which TrunkDO writes into the note's `decisions`. A deterministic proof that decided alone appears in the note's evidence checks (`deterministic: ...`, `gate`). `ft why` and the Why tab show the revision history, directives, note and the decide arc.

**Revert** (`POST /api/colonies/:id/landings/:ref/revert {reason, by?, redo?, proposal?}`, `ColonyDO.revertLanding`, `ft revert`; `ref` is a landing id or a trunk commit of 7+ characters). A person undoes a landing as a new trunk commit that puts every path it wrote back to its blob from before (`trunk/revert.ts` plans it; `TrunkDO.revert` writes it through the serialized system-commit path). It is refused (409) when any of those paths has changed since, naming each path and the latest landing that moved it, or when it would delete a file that trunk files import, naming the importers; both checks run again inside the commit. The intents the landing completed come back as new intents (parent: the reverted intent, why: the reason first; `redo: false` declares none), and a rule's violations count again until they land. The revert commit carries `FT-Revert-Of` and a lineage note with `revert {of, commit, by, reason}`; certification runs on the result; a revert can itself be reverted, which withdraws the intents it declared again (ColonyDO keeps each revert in `reverts`). With `proposal` (`ft revert <colony> <prp_...>`), only that proposal of the landing is undone: its own paths (the landing's recorded paths, filtered by the proposal's write set in the note), with every guard applied to them, and only its intent comes back. The commit carries `FT-Revert-Proposal`, the note's `revert` names the proposal, and a trunk writer still on older code refuses the call (503) rather than undo the whole landing.

**Landing notices.** When a landing changes files that agents still working hold in their footprint (never its authors), each gets one directive of kind `landing` with the landing, the changed paths and their blobs before and after, and the landing intent's title and why: facts, never instructions. An in-platform agent that has not proposed yet rebases on trunk's tip and re-reads the changed files (at most twice); after proposing it does nothing, since the lane catches staleness. MCP agents read notices in their inbox. The `directive` event carries `kind: "landing"`, the landing id and the paths.

**Events**: `amended`, `withdrawn`, `retracted`, `reverted`, `directive` and `status` (plus `intent` with status `withdrawn`). The Events tab groups the first five under Direction; the Intents tab shows an `rN` badge on amended intents and groups intents by what asked for them, then by region, each rolled up by state and sorted most urgent first (`packages/web/src/intentTree.ts`).

## Stuck work

`colony/stuck.ts` checks, from indexed queries, for work that stopped moving: an intent claimed with no change for 10 minutes (with the agent's own note), an intent whose changes came back 3 or more times (with the last reasons), certification red for 15 minutes (with where its repair stands), a report or a change waiting 10 minutes for a person, and an agent alive but not moving for 10 minutes. The snapshot and the metrics report carry `stuck: { at, items, total }`; each item says what to do (review the change, answer the report, look at the agent, amend or withdraw the intent, look at the tests), on the needs-you strip and in `ft status`. The colony's tick, at most every 30 s, publishes one `stuck` event per new item (`stuck_reported` keeps the keys); an item that clears publishes nothing, and one that recurs is reported again.

## Escalations

An agent that finds an intent cannot be done as written (a wrong test, a contradictory spec, an impossible ask) reports it instead of working around it: the MCP tool `escalate {intentId?, kind, report}`, or an in-platform agent's `ESCALATE <kind>: <report>` reply. `ColonyDO.escalate` keeps the report on the intent (`escalation`: kind, report, agent, time), releases the agent's claim and lease, and keeps the intent out of `take()` until a person answers; at most one report waits per intent. A person resolves it with `POST /api/colonies/:id/intents/:iid/escalation {decision: "amend" | "withdraw" | "dismiss", note, by?, amend?}` (or `ft escalation`): amend applies the change through `amendIntent` and reopens the intent, withdraw withdraws it, dismiss reopens it unchanged. `GET /api/colonies/:id/escalations` and `ft escalations` list the open reports; the web Review tab shows them as cards. The repair intents of certification tell their writers to escalate a wrong test with kind `broken-test`. Checked on a preview (2026-10-13) with `scripts/mcp_escalate.ts`: an external agent escalated over MCP, no agent could take the intent while the report waited, and a person's dismissal reopened it.

## Contest mode

An intent declared with `contest: n` (2 to 4; API, spec `intents[].contest`) is raced by up to n agents at once: contestants' claims on its files neither repel nor inhibit each other, and later contestants skip admission. Each contestant's change goes through the decide arc as usual; a contest change that reaches ready is held until every live contestant has one ready or ten minutes after the first (a contestant that gives back, stops or dies does not block). Then `decide/contest.ts` picks one: a deterministic proof first, then fewer residual paths, then no danger signals, then a pairwise comparison by a second-opinion model outside the authors' families, asked in both orders so a disagreement counts as a tie, then the smaller diff, then the earlier change. The winner goes to its lane; each other change goes back with `supersededBy` and the reason; contestants still working get a withdrawal notice; the winner's lineage note keeps the others as `alternatives` (proposal, agent, model, why it lost), and a `contest` event is published. If the winner does not land, a new round starts. Judge calls count in the colony's decide spend. Checked on a preview (2026-10-13): three in-platform agents raced one intent (a small formatting module and its tests); the colony held their ready changes, the judge (gpt-oss-120b) preferred whichever change it was shown first in both orders, so the comparison counted as a tie broken by the smaller diff, the winner landed about two minutes after the race began, and its lineage note keeps the two others as alternatives. In an earlier try with a harder task (wiring a new route into the router), none of the 49 changes the three agents proposed passed review, so nothing was compared: a contest only helps when at least one contestant can do the work.

## Agent-scale source control

Anthropic's account of Scion, its in-house version control system for 30,000 merges a day (2026-10-13), lists the principles of source control for agents. Where FireTrident stands on each:

| Scion | FireTrident |
| --- | --- |
| No merge queue; test after merge, before deploy | Lanes land optimistically; certification runs after landing; `certified` moves only to a passing commit; a red trunk becomes a repair intent, and culprit finding names the suspects |
| Commits, merges and rebases on the server | The trunk writer builds every trunk commit by replacing only the changed paths and moves trunk with compare-and-swap; agents never push to trunk |
| Changesets: changed files with content pointers, accepted without coordination; refs moved separately | Inline changes carry their contents; with asynchronous publishing the trunk writer records landings and pushes git beside its cycles |
| Every client query is an API; jobs need no local repository | `why` and blame per line, path history, landings, certifications, review, escalations and the MCP tools; agents read files through the server |
| Sparse and virtual checkouts | Virtual checkouts: agents read only the objects they need, cached by id |
| Derived data through one mechanism | Derived indexes: import index, co-change map, path history, why-context |
| Engineers tell agents "no"; people review a change's intent, not every line | Rules and antibodies keep each "no"; the review card leads with the intent and the lines to look at |
| Permissions per directory; approvals that tell comment-only changes from logical ones | Protected paths always reach a person; comment-only changes land on a deterministic proof |
| Component "superfans" watching telemetry | The stuck-work detector, and the cascade detector |

What differs: Scion leaves git and serves a repository with almost 100 GB of history, checked out on the order of 25 million times a day for CI; FireTrident stays git (any client can clone a colony and read its notes) and has run on repositories of up to 1,287 files. Scion lets concurrent changes conflict and fixes them afterwards; FireTrident also validates what each agent read before its change lands.

## Scale

Every agent talks to one ColonyDO, so the take path is built to stay cheap per call:

- **Shared field reads.** A take scores up to 200 open intents against the claims of the regions they touch. Each region's claim field is read once and shared by the takes running at the same time (`colony/views.ts`), so scoring a candidate costs map lookups instead of glob tests against every claimed path. Results equal core `repulsion`.
- **Take gate.** At most 128 takes score at once; more queue behind them (`TAKES_IN_FLIGHT`). Without the gate the object ran out of memory and reset at 5,000 agents. Waiting agents are paced (`WaitPacer`): each wait gets a retry time that keeps the whole waiting crowd near a fixed rate of takes a second, so idle agents do not retry in step.
- **Pushed outcomes.** When a proposal settles, the colony pushes the outcome to the agent (`AgentDO.outcome`), so in-platform agents stop polling `getProposal`.
- **Live claims only.** Stopping or reaping an agent clears its claims in every region, and admission counts only live claims, so a stopped run no longer holds a region's admission for its claims' decay time.
- **Lease book.** Leasing a workspace is pure SQL (`pool/slots.ts`). Each slot keeps one write token (two hours). A released slot keeps its lessee's token, so the same agent leasing it again needs no control-plane call. An idle slot gets its token revoked and a fresh one minted in the background. A token is never handed to a different agent.
- **Notes fanout.** Lineage notes use git's 2-character fanout layout. Notes written flat before it migrate a slice per flush. After the scale runs, stock git found a note on 5,894 of 5,894 landing commits.
- `FT_LAG_PROBE` (load tests only) makes ColonyDO log event-loop lag and stream it as `colony.lagMs`.

Measured on a preview (`packages/bench/results/2026-10-12-scale/`) with synthetic API agents (no model calls, review off, no work time, 64 regions), 120 s runs:

| Agents | Landings/min | Time to land p50 / p90 | Platform errors |
|---|---|---|---|
| 1,000 | 2,924 | 13.0 / 17.0 s | 0 |
| 2,000 | 2,714 | 14.8 / 19.5 s | 0 |
| 5,000 | 2,778 | 12.5 / 17.4 s | 0 from load; 78 of 50,368 calls failed in the first 33 s: the load generator's own DNS and connection errors, and one reset when the preview's code was updated (`live-n5000.json`) |

These runs predate the event record (see Replay). Their driver held a live feed open, so regions were already emitting field events to the colony; the record adds one batched insert per published batch. Before these changes, 1,000 agents reached 515 landings/min and the run stopped at 60 s with a 38% error rate. The next limit is TrunkDO, the single writer: every 3.4 to 3.9 s commit cycle hits the 200-proposal cap, so throughput no longer grows with agents, and about 6 s of queueing dominates time to land.

Round 4 (`packages/bench/results/2026-10-13-round4/`: preview p18, one colony with 64 regions, the same driver) measured the trunk writer's new modes at 5,000 agents. The git path landed 1,821 a minute: 3.9 s of each 5.1 s cycle went to reading the changed blobs from workspaces (2.2 s on 2026-10-12; the code is the same, Artifacts read latency is not). Inline changes remove that read: the cycle took 2.8 s, 3,842 changes landed a minute, and time to land fell from 19.1 to 10.7 s at p50. Asynchronous publishing moves the push out of the cycle (cycles of 1.8 to 2.5 s, below the 200-proposal cap, and pushes of 6 to 11 s beside them, each carrying 120 to 360 landings; median time to land about 8 s) but did not raise throughput (2,759 and 3,776 a minute): ColonyDO, which answers every take and proposal and the trunk writer's call for inline contents, became the limit, and it slows as the colony's history grows. Two of its costs were fixed on the way: with asynchronous publishing, every take's check for unpublished landings on its files sorted the landings table and parsed the newest 500; it now walks only the landings between the two heads, by an index on `trunk_sha`, and extends its last answer when only the colony's head moved (takes refused for room fell from 10,201 to 237 in a run).

The live bench (`packages/bench/src/live.ts`) leaves its colony and record in place and writes a `run` block: agents joined, trunk commits, changes and intents landed, the span from the run's first landing to its last, landings and changes a minute over it, and time to land at p50 and p95. Its agents call the REST API, which the per-session call budget does not cover (that budget applies to MCP sessions). Production's `scale` colony is such a run.

## Replay

ColonyDO records every event it publishes (`publish` in ColonyDO, `EventRecorder` in `colony/events.ts`) into a capped `events` table: a sequence number, a time, the event type and the event, the newest 100,000 kept. Field marks are not recorded (the replay derives the field from intents, claims and landings); metrics are sampled every 3 s while events flow, plus one trailing sample. Recording happens where events are published, so it does not depend on who is watching or how live delivery is batched; regions therefore keep emitting while a colony works, even with no viewer.

`GET /api/colonies/:id/events?after=<seq>&limit=<n>` pages the record. A colony that ran before recording existed answers with a timeline rebuilt from what it stores (`colony/replay.ts`: rules, intents with their times, agents, proposals and their decide outcomes, decisions, landings with their files, revisions and directives), labeled `reconstructed`; claim times and the deaths of reaped agents are estimated. The web app's `/c/:id?replay=1` feeds the record through the same reducer as live events, at 1× to 16× with a scrubber; director mode (`?director=1`) works on top of it.

The colony page holds thousands of agents: agents are canvas dots, a map of more than 2,000 files is laid out again at most once a second while files keep arriving, a seek backward in a record of more than 20,000 events waits until the scrubber rests (250 ms), and proposals are pruned once per batch of events.

## New projects (`ft new --spec`)

A spec (see `demo/new-project-spec.md`) declares the project's intents, the files each one builds on, the spec sections every agent receives, an optional model per intent, the architecture rules, and acceptance tests. `ft new` creates a colony with an empty trunk, sets its policy first when the spec declares one (`policy`: `protectedPaths`, `commentProof`; `POST /decide/policy`, so no agent can change a protected path before it holds), adds the rules, and posts the intents in dependency order (parents and priorities make foundations land first). An in-platform agent waits until the files its intent builds on have landed, reads them, and writes files that must parse, keep every rule, use only TypeScript that Node can strip, and import only files and names that exist; each file gets up to three attempts with the failure as feedback. `demo/run_new_project.rb` runs the flow and verifies the result from a plain git clone.

## Plain-git access

A colony's trunk can be read with stock git and no account: `git clone https://<host>/git/<colony>.git`, then `git fetch origin refs/notes/firetrident:refs/notes/firetrident` for the lineage notes (`api/git-proxy.ts`, mounted at `/git/*`).

- Only `GET /git/<colony>.git/info/refs?service=git-upload-pack` and `POST /git/<colony>.git/git-upload-pack` are forwarded, to `<colony>--trunk` in `ft-trunk`. `git-receive-pack` (push) gets 403 with a plain-text reason that git prints as `remote: ...`; every other path is 404.
- Only colonies listed in `FT_PUBLIC_GIT` (comma-separated) are served; empty or unset turns the proxy off. The name in the path must be a colony slug (lowercase letters, digits and single hyphens, at most 48 characters), so no other repo is reachable.
- Read-only by construction: the Worker mints a read token for the trunk with `mintToken` (30 minutes, replaced 5 minutes before expiry, cached per isolate) and adds it upstream. Clients never see it. When the remote refuses the cached token, the ref advertisement retries once with a fresh one; a 401 is never passed on, because git would ask for a password.
- Protocol v2 passes through (`Git-Protocol`), and v0 still works. Bodies stream both ways with their content types. Gzip request bodies (git compresses requests over 1 KB) are decoded in the Worker, and a request body is capped at 4 MiB both as sent and after decoding (413).
- `/git/*` is in `run_worker_first`: without it, static assets answer GET requests under `/git/` with the UI. So is `/`, matched exactly: a request for `/` that prefers `text/markdown` gets `start.md`, and every `/` response carries `Link: </start.md>; rel="service-doc"` and `Vary: Accept`. The page holds a static summary inside its root element (the pitch, the production runs, the clone, notes and verify commands, the public MCP command) that the app replaces when it loads, and `/llms.txt` and `/start.md` answer five questions with one measured number and one link each. `GET /api/about` names the serving build: the commit (`FT_BUILD`, set by the deploy script), the version id and tag (the version metadata binding), the deploy time, and the names of the flags that are on.

Measured on a preview (2026-10-12) with a Hono trunk imported at depth 200 (583 files, 2.4 MB pack) and one landing: clone 1.9 s median over 5 runs; clone, notes fetch and `git log --notes=firetrident -3` together 2.9 s median.

## Trunk certification

Review decides whether a change may land; trunk certification checks that trunk still works. After landings the colony runs the project's own tests on trunk and records the result per commit (`packages/worker/src/certify/`).

- **When.** `ColonyDO.onLanding` (and FireTrident's own commits) only marks trunk as moved; no landing waits for tests. At most one certification runs at a time and it certifies trunk as it is when it starts, so when landings come faster than runs only the newest trunk is certified; runs start at least `minIntervalMs` (2 s) apart (`schedule.ts`).
- **What runs.** Every `*.test.ts` and `*.test.js` file (under `test/` or anywhere else) that imports `node:test` and reaches no package and no Node built-in the runner lacks (file system, processes, sockets); others are listed with the reason. One `TrunkDO.certifySnapshot` call lists trunk's `.ts`/`.js`/`.mjs`/`.json` files at one commit, and `TrunkDO.readBlobs` reads the test files and, level by level, what they import (at most 400 modules, 4 MB, 512 KB a file). TypeScript is transpiled with sucrase's typescript transform the way Node runs it: types erased, imports that are not `import type` kept, and enums, namespaces and parameter properties failing to load as under type stripping. Imports resolve exactly as written, so a missing file fails its importer, as under `node --test`.
- **How.** All test files run in one Dynamic Worker (`env.LOADER.load`, `nodejs_compat`, `globalOutbound: null`, no env or bindings, CPU and wall-clock limits; the report comes back as a stream read to at most 4 MB and stopped at the run's deadline), each with its own copy of the modules it reaches (keys `t0/src/http.ts`, `t1/...`), so module state does not pass from one file to the next. That is less isolation than `node --test`, which gives each file a process: the files of one run share globals (`globalThis` and the built-in objects), so a file that changes one can affect the files after it, and when a copy per file would exceed 6 MB of code, all files share one copy. `node:test` imports go to a shim (`shim.ts`): test/it/describe/suite with nesting, the (name, options, fn) forms, skip/todo/only, async functions and done callbacks, `t.test` subtests, before/after/beforeEach/afterEach at file, suite and test level, `t.plan` with `t.assert`, `t.mock` (the runtime's) and per-test timeouts (10 s); `node:assert` and `node:assert/strict` are the runtime's own. Counts follow `node --test` (tests = pass + fail + cancelled + skipped + todo). Tests run one at a time, and start from the request rather than while modules load (module evaluation allows no timers), so a file that awaits its own tests at top level never finishes loading. A file whose runner cannot start (for example after an earlier file broke a global the shim uses) counts as a failing test, so it can never drop out of a green run unnoticed; when the very first file's runner fails, before any repository code ran, the run is an error rather than a red that would declare a repair.
- **Reuse.** A test file's results are keyed by what it reaches (paths and blob ids of its import closure, the runner, the per-test limit): a run executes only the files whose key changed and reuses the rest, and a commit whose tested files all match an earlier run reuses that verdict (`reusedFrom`). Results are kept per file only from runs where each file had its own module copy, never from a run that shared one, and never for a file that failed to load or ran out of time.
- **Results.** Stored per commit in ColonyDO (`green`, `red`, `error` or `skipped`), published as a `certify` event (so replays show it), and added to the certified landing's lineage note as `certification` (TrunkDO rewrites the note; its next notes flush pushes it, beside the landing cycles). Green sets `greenSha` and moves the trunk repository's `refs/heads/certified` to the commit (`TrunkDO.markCertified`: forward only, compare-and-swap on the remote; a reused verdict counts), so plain git can check out the newest commit on which every test file certification could run passed (deploy, release and pin from it; `main` holds every landing, tested or not); red keeps the last green. A run is not green when it lost tests since the newest green run: a test file that ran then and did not run now (left out, unloadable or deleted), or a test that passed then and is now skipped, todo or gone. The lost files and tests are listed as failures, so the repair loop picks them up. The trunk bar shows a check or a cross on the head ("60/60 tests", "5 failing", names and errors on hover); `ft status`, `ft watch`, `ft why`, `ft certify` and the Why tab show the same.
- **Culprit finding** (`certify/culprit.ts`, `FT_CULPRITS`). For up to 10 failing test files, a red run compares each file's import closure at the red commit with the last green one and asks the per-path landing index for the landings since that changed those paths (for a file new since green, the landings that added or last changed it and its closure), newest first, at most 3 a file, within 3 s and failing open. The result's `suspects` (landing, proposal, intent, paths, commit) appear in `ft certify`, on the certification card with `ft revert <colony> <prp>`, and, fenced as data, in the repair intent's why.
- **First red commit** (`certify/bisect.ts`, `FT_BISECT`: `on` or a list of colony ids). After a red result is stored and published, the colony searches in the background for the first commit its failing tests fail on: it takes the landings between the last green commit and the red one from the trunk writer's landing log (`TrunkDO.landingRange`, at most 512), runs only the failing test files (lost tests excluded) and their import closures at the red commit first and then halves the range, each run in the same no-network Dynamic Worker, at most 8 runs, 20 s a run and 60 s in all. A found commit names its landing, the intents landed in it and the proposals in it whose writes touch the failing tests' closures (from the landing's lineage note, with the suspects as the fallback); the result gains `firstRed`, a `bisect` event says so, and the open repair intent's why gains a fenced paragraph naming it (edited in place, so no change in flight is sent back). With no green commit to start from, tests that pass alone at the red commit, an error or a bound reached, it ends `inconclusive` with the reason. It never delays a landing or the result; a colony restarted mid-search leaves that result without `firstRed`.
- **Tests before landing** (`certify/preland.ts`, `FT_PRELAND`: `on` or a list of colony ids; per colony, the certify policy's `prelandPaths` globs, empty meaning every change that reaches a test file). In the decide stage, before the gate and never inside a trunk cycle, a covered change's files are laid over the trunk index at its base (inline contents or workspace blobs), the test files whose import closure reaches a file it writes or adds are selected (at most 5, nearest first) and run in certification's sealed Dynamic Worker, and each is judged against trunk's stored result for that file's closure at the base: a test that passed on trunk and fails with the change sends it back to its agent naming the test and its error; a test already failing on trunk is not held against it. A time-out (2 s), a runner error, no trunk result to compare with, or three runs already going (after a 1 s wait) let the change go on as before, recorded as "tests before landing: not checked" with the reason. A colony with review off takes the decide path for the tests alone. The run goes into the change's evidence and its lineage note (`preland`), so `ft why`, the Why tab and the review card show it. Read-set validation still runs at landing: a change tested on its base can still go stale.
- **Repair loop.** A red result with no repair intent open declares one (`repair.ts`): "Make the failing tests pass: <names>", source `certify`, priority 10 (spec intents use 1 to 5), footprint the source files the failing tests load (nearest first, at most 6), the failing test files and their other imports as "Builds on" context (the tests are the specification and are not to be edited; a writer that thinks a test is wrong gives the intent back with the reason), the failing tests with their errors and the spec context of the intents that wrote those files in its `why`. At most one is open, and at most `repairsPerHour` (3) are declared in an hour. A repair owes the tests it was declared for (`certify_repairs`): a run satisfies it only when each of them ran and passed, and until then the run is red and the repair stays open. Withdrawing a repair accepts its losses. Agents take it like any other need.
- **Switches.** `FT_TRUNK_TESTS` = `on` for a deployment (binding `LOADER`); per colony, `POST /api/colonies/:id/certify/policy {enabled, repair, repairsPerHour, timeoutMs, testTimeoutMs, minIntervalMs}`. `GET /api/colonies/:id/certifications[/:sha]` reads results; `POST /api/colonies/:id/certify` certifies the current trunk now.
- **Checked.** `test/certify/run.test.ts` runs fixture projects through the pipeline in Node and matches `node --test` count for count; `test/do/certify/` runs real Dynamic Workers; `sandbox.test.ts` there shows a test file's `fetch` and socket refused and its `process.env` and Worker env empty (with the sandbox removed, the same file reaches the network). On the two production shortlinks trunks the counts equal a plain clone's `node --test`: 60 of 60, and 67 tests with 62 passing (the same five failures).
- **Measured on a preview (2026-10-12).** Certifying the 60-test shortlinks project took 121 ms from start to result (trunk index 26 ms, reads and transpiling 53 ms, Dynamic Worker 42 ms). Landing latency, two colonies side by side, 6 agents each landing a new test file (so every certification has new tests to run), 75 s runs in alternating order: time to land p50 1.26 and 1.23 s with certification on, 1.37 and 1.42 s off (p90 1.78 and 1.72 s on, 2.34 and 2.30 s off); certifications took 160 ms at p50 with suites up to 3,917 tests in 392 files. Without per-file reuse, rerunning every file added about 0.1 s to mean time to land under that load.
- **On production (2026-10-12).** Certifying `shortlinks-review` (the second run of the new-project spec, made before certification existed) took 267 ms and found the five failures a plain clone shows. The repair loop then ran on its own: the first repair intent landed 11.5 minutes later and left one router test failing, so the colony declared a second; one attempt at it was returned by the second opinion for compile errors and two were given back, and the fourth landed 67 minutes after the first certification. Trunk was certified green at 67 of 67, and a plain clone agrees (acceptance 7 of 7). Evidence: `packages/bench/results/2026-10-12-prod/shortlinks-review-certify-*`.

## Configuration and deployment

- Tuning variables: `FT_COCHANGE_WEIGHT` (co-change repulsion weight, 5 in production), `FT_LATERAL_INHIBITION` (inhibition threshold as a fraction of a fresh claim, or `off`), `FT_IMPORT_WEIGHT` (import repulsion in take; off when absent or 0) `FT_REVALIDATE` (import-name revalidation: `on` or a list of colony ids; off when absent) `FT_DELETION_GUARD` (the deletion guard), `FT_INLINE` (inline changes through the API and MCP), `FT_VIRTUAL_CHECKOUT` (agents read trunk object by object and propose inline), `FT_ASYNC_PUBLISH` (asynchronous publishing), `FT_CULPRITS` (suspects on red certifications), `FT_BISECT` (the first red commit), `FT_EXPORT_GUARD` (the export guard), `FT_TWINS` (twin intents), `FT_PRELAND` (tests before landing), `FT_QUOTED_ACCEPTANCE` (quoted acceptance), `FT_A2A` (the Agent2Agent handoff), `FT_TEXT_MERGE` (text merge), `FT_GOAL_CONFLICT` (the goal-conflict check), `FT_MEGAFILE` (the megafile alarm), `FT_FIELD_GUIDE` (the field guide) , `FT_RESOLVER` (the conflict resolver, with `FT_RESOLVER_MODEL`), `FT_MERGE_INSERTIONS` (insertion merges) and `FT_MODEL_STEPUP` (the stronger model after two returns): each `on` or a list of colony ids, off when absent. `FT_AGENT_CALL_BUDGET` (`on` or `<rate>,<burst>`) is global. `FT_PUBLIC_MCP` lists the colonies the public read-only MCP serves, like `FT_PUBLIC_GIT`. Production sets `FT_INLINE`, `FT_VIRTUAL_CHECKOUT`, `FT_CULPRITS`, `FT_BISECT`, `FT_DELETION_GUARD`, `FT_TEXT_MERGE`, `FT_MERGE_INSERTIONS`, `FT_GOAL_CONFLICT`, `FT_MEGAFILE`, `FT_FIELD_GUIDE`, `FT_RESOLVER`, `FT_MODEL_STEPUP`, `FT_TWINS`, `FT_QUOTED_ACCEPTANCE`, `FT_A2A` and `FT_AGENT_CALL_BUDGET` on, signs lineage notes (`FT_NOTE_KEY`), and sets `FT_PUBLIC_GIT` and `FT_PUBLIC_MCP` to its showcase colonies (`hono`, `shortlinks`, `byo-demo`, `scale`, `order-backend`, `signed-notes`, `first-red`); asynchronous publishing, import-name revalidation, import repulsion, the export guard and tests before landing are off there (the last two have a measured cost, and testing after landing is the default by choice). A changed flag reaches each Durable Object when it restarts on the new deployment, so for a few minutes a colony object and its trunk writer can disagree; a colony's status shows its trunk writer's publishing mode (`publish.on`). `FT_TEST_PUSH_DELAY_MS` holds every push open for that long; it is a test hook for previews and is never set in production.
- What each mechanism buys and costs, measured with it off and on, with each run linked: [README, What each mechanism buys](../README.md#what-each-mechanism-buys). The landing page's Try panel (`web/landing/tryit.ts`) calls the same core functions the trunk writer, the decide stage and the colony call, with production's options; it never touches the API.
- `FT_TRUNK_TESTS`: `on` certifies trunk after landings with the colony's own tests (see "Trunk certification"); needs the `LOADER` Worker Loader binding (Dynamic Workers).
- `FT_PUBLIC_GIT`: colonies served read-only over plain git (see "Plain-git access"); production lists `hono,shortlinks,byo-demo,scale,order-backend,signed-notes,first-red`. A preview sets its own with `npx wrangler preview --name <x> --var FT_PUBLIC_GIT:<colony>`.
- Secrets: `FT_ADMIN_TOKEN` (mutating API routes), `FT_MCP_TOKEN` (`/mcp` and `/sse`), `FT_NOTE_KEY` (the Ed25519 key that signs lineage notes; optional), `ANTHROPIC_API_KEY` (optional Claude agents). Without its token, the API refuses writes and `/mcp` refuses connections (fail closed); `FT_OPEN_WRITES=1` lifts that for local development only and is never set on a deployment. A preview gets its own with `npx wrangler preview secret put FT_ADMIN_TOKEN --name <x>`.
- `wrangler.jsonc` has a `previews` block that mirrors every production binding, so `npx wrangler preview --name <x>` gives an isolated deployment with its own Durable Objects. Previews share the Artifacts namespaces with production, so a preview colony must not reuse a production colony's name.
