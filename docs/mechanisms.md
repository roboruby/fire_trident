# Mechanisms

How FireTrident coordinates many agents on one repository, what each mechanism buys and costs, and which flags turn each on. Plain terms come first; the names the code uses (colony, field, antibody) are in [glossary.md](glossary.md), and the Durable Objects, routes and contracts are in [ARCHITECTURE.md](ARCHITECTURE.md). Measured runs are in [results.md](results.md).

## How it works

Git platforms coordinate people through things they lock, queue and gate: branches, pull requests, a merge queue, a reviewer. A merge queue lands one change at a time, each after a test run on the tree it will land on (a selective queue runs only the tests the change reaches; the simulator models a full run), so it lands tens of changes a minute however many agents wait, and checking every waiting change against every other grows as the square of the agents (80 agents are 3,160 pairs a wave). FireTrident answers with a combination: optimistic landing, validated against the files each agent read; agents driven by real models; deterministic review before any model is asked; testing of trunk after landing; and signed lineage in git. Its trunk writer folds up to 200 proposals into one 2 to 5 s trunk cycle without rebasing any (2,730 changes a minute measured on the live service). The code names its parts after natural systems that coordinate through shared signals instead of a central queue (ant colonies, slime molds, immune systems).

People declare the target state: architecture rules plus tests (the *target morphology*, in the code). Every rule violation becomes an open intent, and the agents work until there are none.

### Choosing work

Agents coordinate through marks the platform leaves on the code, not through messages to each other: a claim lease on the files an agent holds, a need for each open intent (its priority, growing with age), a trail on files recent landings changed, and failure and danger marks. Marks fade with time; together they are the *field*. When an agent takes work, an open intent's need draws it, and claim leases and danger marks on the intent's files push it away; trails and failures are there to read (in `sense`, on the map and in replays) and do not steer a take. Each region's marks are read once and shared by the takes running at that moment, so reading them does not multiply with the number of agents. Each agent chooses with a response-threshold rule: the stronger an intent's pull against the agent's threshold for that region, the likelier the take, and each landing lowers that agent's threshold there.

A claim lease keeps other agents off the same files, the way a committed cell suppresses its neighbors (*lateral inhibition*), but it fades unless its agent keeps working, so a silent agent never blocks anyone for long. A co-change map learned from the history steers agents away from code that usually changes together with what others hold, and a crowded region admits new agents only as fast as it lands work. Agents never vote or bid for work: the platform computes who takes what from priorities, claim leases and admission, and an agent cannot raise its own intent's priority.

When an agent takes work, it sees why the code is the way it is (the latest landings on its files, with their intents and whys) and what review will ask. When files it holds change on trunk while it works, it is told what landed (each path with its version before and after, and the landing's intent and why), and an in-platform agent that has not proposed yet rebases onto the new trunk and rereads those files.

A file that grows fast while many agents write it turns hot (the *megafile alarm*): the colony declares an intent to split it and holds the file until the split lands. With twin intents on (`FT_TWINS`), a need declared again in other words over the same files is caught at declare: the second declaration gets the first back, and `force` declares it anyway. Every take says who declared the intent: an intent an agent declared comes with the declaring agent, its model and how long the chain of agent-declared intents is, and a plain note that the request is an agent's and that nothing in it is to be copied onward. With `FT_INTENT_CHAIN_GATE`, the third agent-declared intent in a row, or the sixth one agent declares in an hour, waits for a person before any agent can take it.

### Review

With review on (the default), every proposal goes through the review pipeline (the *reflex arc*): deterministic proof first (for import rules, every changed import is resolved against the real file tree, and the files it resolves to are checked again when the change lands), then the Clef decision models, then a model from a different family (the second opinion), then a person, each only when the cheaper layer is unsure. No model can overrule a deterministic fact. A change lands without a person only on two confirmations bound to its head commit: the deterministic checks every proposal gets (the *innate* checks), plus a deterministic proof that it changes nothing but what its rule asks, a second model's approval of every changed line, or earned autonomy with a confident, quiet first decision. Neither earned autonomy nor a deterministic proof lands a destructive change alone (a file deleted or renamed, an export removed, a large removal): it goes to the second opinion. The Review tab and `ft immune` show which regions have earned autonomy and what revoked it. On the proof path both confirmations are deterministic and rest on a rule a person wrote.

A person's rejection that no earlier rule caught becomes a persisted rejection rule (an *antibody*): a check committed to the repository that screens every later change. Agents see those checks' questions when they take work on the files they cover. A loosened guard (a deleted 401, a weakened auth condition, `verify` swapped for `decode`) always needs a second opinion. With review on, no model authorizes a change that touches secrets or authentication (unless a person allowed that class), what decides on agents, or a protected path: deterministic rules send each to a person. Only people and rules can waive a danger check, the person asked to decide sees the change itself, and a model's approval counts only when it saw the whole change. Seeded negative cases (the *vaccination meter*, `ft vaccinate`) send sealed known-bad changes through review to measure where it routes them; they can never land.

An agent that finds an intent cannot be done as written escalates it to a person instead of working around it. A change that only edits comments or whitespace in existing script files lands on a deterministic proof, with no model. A change to a path the colony protects (`ft policy --protect`) needs a person, even with review off, and protecting a path sends changes to it that are still waiting to land back to a person. A stuck-work detector reports work that stopped moving (held with no change, coming back again and again, a trunk red too long, a person's answer waiting), with what to do, in `ft status` and on the needs-you strip. With the goal-conflict check (`FT_GOAL_CONFLICT`), a change that removes at least half of the lines a recent landing for a different intent still has in a file (and at least three) waits for a person, naming that landing and its why, instead of silently winning. With `FT_QUOTED_ACCEPTANCE`, a model's approval of a change for an intent with an acceptance list counts only when it quotes, for each line, a changed line that meets it, and the platform finds every quote in the diff it showed; a line not met sends the change back naming it. Every model call in every recorded run was a real call, priced as it happened.

### Landing

Each region of the code has a lane. Lanes batch non-conflicting proposals and validate every file each agent read, not just what it wrote: the platform records each read with the blob the agent saw, so nothing is declared and any change to that file counts. A lane takes waiting proposals in priority and age order and adds each one to the batch when nothing it writes is written or read by a proposal already in it and nothing it reads is written by one (path-disjoint batching, up to 50 a batch). One trunk writer takes every waiting lane batch each cycle (up to 200 proposals), commits each batch on top of the last, and pushes the tip once with compare-and-swap. It waits for no test run and no person: with 1,000 to 5,000 synthetic agents, a cycle took 2.8 to 5.1 s at the median.

A stale change does not always go back. With text merge on (`FT_TEXT_MERGE`), a change stale only on files it writes lands when each of them merges cleanly line by line, as git's default merge does, and its lineage note records the merge; overlapping edits still go back, naming the conflicting hunks. With the conflict resolver on, overlapping edits that text merge cannot combine go to one model call asked to keep both. The merge must match the clean merge outside the conflicting hunks, keep every line either change added inside them, in that change's order, and take neither side's version whole; then it goes through review like any change. With import-name revalidation on (a flag, off in both configs), a change that is stale only because a file it read changed still lands when every name it imports from that file is still exported, instead of being redone.

Several agents can race one intent (contest mode): the colony picks the change to land by deterministic evidence (a proof, fewer changed paths outside the footprint, no danger signals), then by a second-opinion model asked in both orders, where a disagreement counts as a tie broken by the smaller diff, and keeps the others in the winner's lineage. The second opinion is one judge from a different model family than the agent that wrote the change. A cascade detector watches the branching ratio of stale returns and slows a region down before a rebase avalanche spreads.

A proposal can carry its file contents (an inline change, checked against git's blob ids), so the trunk writer never reads it back from a workspace, and an external agent can propose over MCP with no git at all. With virtual checkouts, in-platform agents read only the trees and blobs they need instead of cloning. With asynchronous publishing, the trunk writer records landings in its own storage and pushes trunk to git beside its cycles, and a take that would start on a base without a fresh landing on its files waits a moment. A change of direction takes effect at the trunk writer: a withdrawal or amendment either stops a change in flight or names the landing it lost to.

### Testing after landing

No landing waits for a test run. Right after landings, the colony runs the project's own tests on trunk in a Dynamic Worker with no network, no environment and no bindings, the only place FireTrident runs a repository's code. A passing commit moves the `certified` branch, the branch to deploy, release and pin from, which only ever points at a commit on which every test certification could run passed; a failing trunk becomes a repair intent that agents take like any other need. A repair counts only when the tests it was declared for run and pass, and `certified` never moves on a run that lost tests.

A red result names its culprits: the landings since the last green commit that changed the failing test's import closure, each with `ft revert <colony> <prp>`. With `FT_BISECT` the colony then runs the failing tests alone at earlier commits, halving the range, and names the first commit they fail on, its landing and the proposals in it that touched those tests' imports. On a preview, a 40-landing history took 6 test runs and a 100-landing one 7, the fewest possible for each (`scripts/bisect.ts --landings 40`, `--landings 100 --break-at 7`). A person can undo any landing, or one proposal of it, with `ft revert`; it is refused when work has landed on top.

With `FT_PRELAND`, a colony can also run, before a change lands, only the test files its change reaches (at most 5) on its base in the same sealed Worker; a test that passed on trunk and fails with the change sends it back naming the test, and anything else (a 2 s time-out, no trunk result, three runs already going) lets it land as before, recorded as not checked.

### Lineage

The trunk writer writes each landing's lineage note itself, from the colony's own record, as it lands the change. Every landed commit carries `FT-*` trailers and that JSON note under `refs/notes/firetrident`: the intent, the rule and who approved it, the agent and model, every decision with its probability, the checks, what the agent did not verify, and the exact files read and written, with their blob ids. Any git client can read it, and the showcase colonies need no account. Each note also says how its author and model are known: a model FireTrident's own agent called is `observed`, with its calls and tokens; an external agent's model is `declared`, as the agent named it. Each commit landed since notes were sealed (2026-10-14) carries its note's SHA-256 as its last trailer, `FT-Note`, so a note edited after landing no longer matches its commit: `ft verify <colony>` checks it, and so do a stock clone and `scripts/verify_note.mjs`, a short Node script. Agents can leave a one-line lesson with a change; it reaches later agents, labeled with its author and model, only after its change certifies green or a person approves it. The landing page shows a live sealed note and how to check it again with stock git. With a signing key set, the trunk writer also signs each commit it builds (Ed25519, over the note's digest, the tree and the parents) and publishes the key at `/.well-known/firetrident-keys.json`, so a check says who wrote the note, not only that it is intact. The note lives in git and outlives the agent and its machine: nothing has to be awake to answer why.

### Model spend

Each colony prices its own model calls as they happen (its agents, review, the contest judge, the conflict resolver) at Workers AI list prices, in total, by layer and per landed intent, from the tokens it counted: the top bar, `ft status` and `GET /api/colonies/:id/metrics` show it as model calls this platform made (an outside agent's own model spend is not on it). A person can cap a colony's spend with a reserve kept for review (`ft spend-cap <colony> <usd> --review-reserve <usd>`): each call is reserved before it starts, and at the cap the colony pauses itself, so nothing lands on a skipped review. Where `FT_INTENT_SPEND` is on, each intent's own calls are priced too (`GET /api/colonies/:id/intents/:id/spend`, the Intents tab, `ft intent show`).

## The review policy

Review reads one policy per colony; its defaults are `DEFAULT_POLICY` in `packages/worker/src/decide/policy.ts`. A person changes them with `POST /api/colonies/:id/decide/policy` (admin token), and each number is clamped to its range.

| Setting | Default | What it does |
| --- | --- | --- |
| `enabled` | on | Runs the review pipeline on every proposal; off, only protected paths still reach a person |
| `deterministic` | on | Lets a deterministic proof confirm a change with no model |
| `commentProof` | on | Lets a change that only edits comments or whitespace in existing script files land on a deterministic proof |
| `confidence` | 0.8 | A model layer acts alone only when the answers that decide are at least this confident (\|2p − 1\| for a yes or no answer) |
| `hit` | 0.5 | A yes or no detector answer at or above this probability counts as a hit |
| `needsHuman` | 0.5 | The probability that a change needs a person must be below this for a model's approval to land it |
| `alertsPerHour` | 30 | Escalations to a person in a rolling hour; past it, one below `budgetRiskFloor` goes back to its agent (protected paths, goal conflicts and a few others never do) |
| `escalationBatchPerHour` | 60 | With `FT_ESCALATION_BATCH`, escalations the hourly alert budget cannot send back get a budget of their own, per colony; past it, each still waits for a person, and the batchable ones that escalated for the same reason show as one card: approve all, reject all, or open each |
| `budgetRiskFloor` | 2 | The risk (0 none to 3 high) at or above which an escalation still reaches a person once the hour's budget is spent |
| `autonomyAfter` | 3 | Landings a deterministic proof, a second opinion or a person approved in a region, since its last revocation, before the reflex may land there alone |
| `probation` | 0.1 and 0.25, after 5 fires | A detector overruled (by a higher layer or a person) at least 10% of the time becomes advisory, recorded but no longer deciding; more than 25%, off, no longer asked; once it has fired 5 times |
| `maxAntibodies` | 60 | Matching persisted rejection rules (antibodies) asked per proposal, in one Clef call |
| `llmConcurrency` | 8 | Second-opinion calls in flight at once, per colony (the contest judge has a limit of its own of the same size) |
| `llmPerMinute` | 120 | Second-opinion calls started a minute, per colony and model |
| `goalConflictMinutes`, `goalConflictLandings` | 60 and 200 | With `FT_GOAL_CONFLICT`, a landing counts as recent, so a change undoing its lines for another intent waits for a person, for 60 minutes and while it is among the newest 200 landings |
| `intentChainDepth` | 2 | With `FT_INTENT_CHAIN_GATE`, the third agent-declared intent in a row waits for a person |
| `intentFanout` | 5 | With that gate, the agent-declared intents one agent declares in an hour past these 5 wait for a person |
| `reflexModel` | Clef | The decision model asked first |
| `secondOpinionModels` | Gemma 4 26B, gpt-oss-120b, GLM 4.7 Flash | The second opinion: the first of these from a different model family than the change's author |
| `juryModels` | Gemma 4 26B, gpt-oss-20b, GLM 4.7 Flash | With `FT_CONTEST_JURY`, the small models seated in place of the contest judge |
| `dangerAllow` | none | Danger classes a person allows without sending each such change to a person, optionally under some paths; a second confirmation is still needed |
| `protectedPaths` | none | Paths only a person may change, at most 50 globs |
| `auditRate` | 0.03 | The share of changes that landed without a person (proof, reproduction, a model or earned autonomy) sent to a person after landing, sampled per confirming layer, 0 to 0.2 |
| `canaryRate` | 0 | The share of escalations accompanied by a sealed known-bad change in the human queue to measure what reviewers catch, 0 to 0.2; off by default |

**People see the ordinary, not only the odd.** A share of the changes that landed without a person (3% by default, per confirming layer) is sent to a person after landing and shown in the review queue between escalations; "should not have landed" offers the revert and revokes earned autonomy, and the answers measure each layer with an interval. Seeded known-bad changes (blind canaries), sealed so they never land, can be mixed into the human queue to measure what reviewers catch.

**How a colony decides.** The colony page names a colony's policy as one of four presets: local development, central development (the defaults above), pre-production or production, or custom with the values that differ, each with one sentence on what lands without a person. Beside it are the last 30 days of landed changes by what confirmed them (deterministic proof, a model, earned autonomy, a person), and every landing card names the rule that confirmed it with the values it used, such as `R3: confidence 0.93 ≥ 0.9, p(needs_human) 0.04 < 0.2, approved landings 23 ≥ 20`. Read it at `GET /api/colonies/hono/decides`; `ft status` prints the preset and the split, and `ft why` the rule. When a change goes to a person, the colony's tests run on it at its base first, and the review card leads with the result against trunk (`ft review <colony> --retest <id>` runs them again).

## How git's ideas map


| Git platform | FireTrident |
| --- | --- |
| Repository | A colony: a trunk repository in Artifacts plus the coordination state around it (the field of marks) |
| Branch, worktree | A workspace: an Artifacts fork leased to one agent with a 2-hour token scoped to that fork, revoked when the fork is reassigned; no token an agent holds can write trunk |
| Issue, assignment | An intent with a predicted footprint, taken by agents by priority, age and the claim leases on its files |
| Pull request | A proposal: write set, read set, evidence, and what was not verified |
| Code review | The review pipeline: proof, Clef, a second model, a person; persisted rejection rules remember every rejection |
| Merge queue | Lanes per region of the code, path-disjoint batches taken greedily in priority order; one commit per batch, and each cycle's batches pushed to trunk together |
| Merge conflict | A change stale only on files it wrote is merged line by line when the edits do not overlap (text merge); otherwise it goes back naming each file that changed under its reads or writes, with the version it read and the version on trunk, or, with the conflict resolver on, a model is asked to merge both, the merge is checked against the clean merge, and it goes through review like any change |
| Competing pull requests for one issue | Contest mode: up to four agents race one intent; one lands, the others stay in its lineage as alternatives |
| "Blocked: the issue is wrong" | `escalate`: the agent reports it and the intent waits for a person to amend, withdraw or dismiss |
| Protected, always-green branch | `certified`: moves only to trunk commits on which every test file certification could run passed; deploy and pin from it |
| `git revert` | `ft revert`: a person undoes a landing, or one proposal of it, as a new commit, refused when work landed on top; its intents come back with the reason |
| Contribution stats | `ft census [<dir>]`: any git clone, offline, credits commits, lines added and lines still alive to coding agents, bots or people, each sealed by an intact lineage note, claimed by a trailer or identity, or inferred from a merged agent branch |
| Codemod | A recipe (on staging, a rename across 212 files landed while 30 agents held edits: none came back, where stock git conflicts on all 30): `ft recipe <colony> rename <old> <new> --scope <glob>` lands a mass rename as ordinary commits and applies it to every change still in flight, so no agent is sent back |
| `git blame` | `ft why`: the lineage of any line, from git notes, skipping formatting-only landings, following moved code, and saying whether each landing still holds |

Most of FireTrident's mechanisms sit behind a flag, and most were measured with the flag off and on. Each row says where: PRODUCTION is the live service, PREVIEW a preview deployment of the same code with its own Durable Objects, SIMULATED the simulator driven by Hono's history. It gives the number the mechanism exists to move, that number with the mechanism off and on, and what it costs. Three mechanisms cost more than they earned where they were measured (asynchronous publishing, import repulsion where nothing contends, and the contest jury), and all three are off in both configs ([Flags](#flags) lists them all).

## Flags

Every flag and tuning variable `packages/worker/wrangler.jsonc` sets, and every flag `packages/worker/src/env.ts` documents, with its value in the stage config (`env.staging.vars`) and the production config (the top-level `vars`). A flag is `on`, a comma-separated list of colony ids, or off when absent; `packages/web/test/docs.test.ts` checks this table against the config. A deployment runs the config it was last deployed with: `GET /api/about` lists the flags the serving build has on. Production also signs lineage notes with the `FT_NOTE_KEY` secret. `FT_TEST_PUSH_DELAY_MS` and `FT_LAG_PROBE` are test hooks for previews, and `FT_OPEN_WRITES` is for local development only; none is set in either config.

## How it uses Cloudflare

- **Artifacts:** one trunk repository per colony (imported from a public git URL, one branch to a depth of 200 commits through Artifacts' own import, or started empty), a warm pool of workspace forks spread across four namespaces, 2-hour repo-scoped tokens that never reach trunk (agents never hold a trunk write token), git notes for lineage, persisted rejection rules committed as files, and a read-only git endpoint that serves the showcase trunks to stock git.
- **Durable Objects:** the colony, one object per region of the code (field, admission, lane), the single trunk writer, the workspace pool, and every in-platform agent.
- **`@cloudflare/computer`:** git inside Durable Objects for the trunk writer and the agents (clone ~350 ms, commit ~90 ms, push ~300 ms).
- **Dynamic Workers:** trunk certification loads each project's own tests into a Worker built at run time, with no network access, no environment or bindings, and CPU and time limits. It is the only place FireTrident runs a repository's code.
- **Workers AI:** Clef decision models answer the review pipeline's typed questions (does this need a person, how risky is it, does it touch sensitive code, is it off its intent, and each matching rejection rule's question), and none can overrule a deterministic fact; Kimi K2.7 Code and Gemma 4 for agents; Gemma 4, gpt-oss-120b and GLM 4.7 Flash for second opinions.
- **Agents SDK** (the MCP server), and static assets on Workers for the colony map.
