Method and assumptions

  • Live (MEASURED). Synthetic REST agents take, propose, and poll their outcome on the in-platform schedule (1.5 s, ×1.6, capped at 15 s). Each proposal writes a new file whose blob already exists in every workspace fork. That makes the trunk writer do the real work (read the blob from the agent's fork, build the tree, push trunk with compare-and-swap, write the lineage note), while the agents need no git of their own. The review prong (reflex and LLM triage) was turned off on the two bench colonies, so the numbers isolate coordination and landing. Latencies are laptop-side and include about 100 ms of internet round trip.
  • Calibration. In-platform take 250 ms and propose 30 ms; lane overhead 100 ms. Trunk writer per commit: 620 ms + 72 ms per proposal (fitted on the swarm runs and a single-region batch experiment). The baseline lands a change in 692 ms (the same writer with one proposal) plus 350 ms to rebase a stale change (fetch and replay, from the Artifacts spike). Checks cost 0 ms in the headline runs, the most favourable setting for the baseline.
  • FireTrident model. Mirrors the deployed code: take scores the 200 oldest open intents with core chooseIntent, using repulsion from claims and admissionOpen per region. Each proposal joins the lane of its primary region, where core validateProposal and selectBatch run. The tick interval is laneIntervalMs × inhibitionFactor(σ), and σ is computed with core branchingRatio over recorded causes, where returns are never parents. One trunk writer per colony serves the lanes' commits one at a time and re-validates each batch. A returned intent reopens and is redone in full.
  • Baseline model. Exclusive locks on write sets, offered from the same 200 oldest tasks, with the same 3 s retry hint. One FIFO merge queue: a stale change is rebased and its checks re-run, and a change whose read or written files changed since its base fails (the same rule as read-set validation). It goes back to its agent, which keeps its locks, reworks half of the change, and resubmits.
  • Not modelled. The coordinator's own request capacity (one ColonyDO per colony) is assumed to scale in the simulator. Live, a single ColonyDO served 1,000 agents with no errors at take p99 3,617 ms. Fork creation is not modelled (the pool is assumed warm).

What changed in RegionDO for the demo

  • σ treats returns as leaves. A returned proposal changed nothing on trunk, so it cannot make anything stale. Counting every event in the window as a parent pinned a burst of N returns from one landing at N/(N+1) < 1 and hid every cascade. σ is now stale returns per landed proposal, with core branchingRatio's window semantics (60 s window, 5 s settle).
  • σ is re-evaluated after the lane empties. While σ > 1, or while a recent return may still raise it, an empty lane keeps a 2 s alarm. Previously σ was sent only after ticks that had proposals, so neither the spike (which arrives after the settle time) nor the recovery reached the UI. An enqueue into an empty lane replaces that alarm, so the inhibited cadence still holds.
  • Inhibition is published. Every alarm sends sigma, and while the factor is above 1 (and once when it lifts) it also sends metric events inhibition:<region> and laneDelayMs:<region>. Deployed 2026-10-12 06:14 UTC; DO tests pass, including a new case where 4 returns from 1 landing give σ = 4.

Findings and open issues

  • Trunk group commit lifts the one-commit-at-a-time ceiling (MEASURED). At 1,000 agents the colony landed 515 changes/min, 3.7× the serial writer's 138/min, with 838 errors and 0 returns across the group-commit runs. The writer ran 24 cycles/min, each landing 11.8 lane batches (16.6 proposals) as chained commits behind one trunk push and one notes push. A cycle took 890 ms at the median: pull 132 ms, build 43 ms, push 517 ms. Each lane batch is still its own commit with its own lineage note, so why stays per landing. The next limits are outside the trunk writer. At 1,000 agents the one ColonyDO that serves every take, poll and propose saturates (overload errors and take timeouts tripped the driver's error guard at 60 s, so that run's rate is measured over a window it only partly worked in), and at 200 agents workspace leasing sets take latency (p50 6 s). Inside a cycle the trunk push is now the largest phase, and lane cadence at low flux sets the time-to-land tail.
  • Fixed: landed proposals reported as returned. A lane's TrunkDO.land call could fail on the lane's side after the trunk writer had landed the batch (the logs show Durable Object reset because its code was updated during deploys). The retry then reported those proposals as already landed in lnd_… (13 times at 1,000 agents), and a lane re-validating them saw them stale against their own new blob (on the Hono run one landed proposal was returned and its intent taken and abandoned 19 times). Outcomes are now idempotent per proposal id: the trunk writer reports earlier landings in prior, and a lane asks TrunkDO.landingsOf before returning a stale-looking proposal, so a landed proposal is always settled as landed.
  • Admission ignores the shared trunk writer. The floor of 3 agents per region admits far more agents than one writer serves when a colony has many regions. With the 200-oldest candidate window and repulsion, contended intents clog the window and are eventually taken anyway. That is why rework is about 42% vs 22% for locks on hono's history.
  • σ is per region. A stale read caused by a landing in another region gets no cause, so cross-region cascades stay invisible to the governor.
  • The review prong triages every proposal (deployed 06:32 UTC). It returned 41 of 87 synthetic proposals and added seconds each, so it was turned off on the two bench colonies with POST /api/colonies/:id/decide/policy {"enabled":false}. The 10-1,000 agent runs predate it. Two other deploys happened during the runs (06:24 and 06:32 UTC); the 200-agent run spans the first.
  • Account use. 286 workspace forks (bench-w2-load 249, bench-w2-cascade 37), 8 seeds, 2 trunk imports. Both colonies are kept for re-runs and video capture; DELETE /api/colonies/:id removes them. The group-commit runs used one more colony on a preview deployment (g1-bench: 253 workspace forks, 4 seeds, 1 trunk import).
